# Finance V1.2 service-code mapping workflow

`011_service_code_mapping.sql` is additive and isolated-only. It stores no mapping values. Room type, care level, meal plan and meal charge type are source domains; each mapping points to a specific item in one versioned price list and is bounded by that price version's effective dates. The database rejects unknown service codes, scope mismatches, unapproved price versions at mapping approval, overlapping approved mappings, self-approval and edits to approved terms. Superseding is an audited state transition with a future effective date; previous terms remain usable through the preceding date.

The authenticated API checks a verified Finance identity, active staff session and explicit capability. ADMIN/SUPERVISOR may draft, submit, approve and supersede; ACCOUNTANT may view approved history. Other roles are denied. `GET /api/finance/service-mappings/resolve/:sourceDomain/:sourceEntityId?serviceDate=YYYY-MM-DD` returns exactly one active approved mapping and the referenced approved price item, or fails closed.

The existing room source is `accommodation_rooms.room_type`; care source values must occur in resident care level or an approved admission care classification. No canonical meal-plan/meal-charge source was found, so the API denies meal mapping creation with `FINANCE_MEAL_SOURCE_UNVERIFIED`. There is no FK fabricated for source identifiers that have no canonical entity table.

The pricing tab now includes mapping administration. Contract pricing-mode evaluation supports explicit PACKAGE, ITEMIZED and HYBRID terms and refuses unsigned terms, ambiguous legacy totals and included-service double billing. It remains a calculation boundary only: the current repository has no invoice generation/issue endpoint to call it or the mapping resolver. No Production Test migration, mapping, price or contract write is authorized by this change. Apply and test only through the disposable PostgreSQL 16 migration suite.
