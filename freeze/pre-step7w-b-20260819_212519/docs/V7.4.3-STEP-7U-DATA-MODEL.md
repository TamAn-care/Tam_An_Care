# Step 7U — Canonical Data Model

Exactly eight domain tables are designed.

## 1. sleep_care_plans

Human-authored sleep/rest preferences and care support plan.

Core concepts:

- sleep_care_plan_id
- resident_id
- preferred_bedtime
- preferred_wake_time
- usual_sleep_pattern
- night_light_preference
- room_environment_preference
- toileting_support_preference
- mobility_support_requirement
- night_check_requirement
- status
- owner_id
- reviewer_id
- created_at
- updated_at

Lifecycle:

DRAFT -> REVIEWED -> ACTIVE -> RETIRED

## 2. sleep_observations

Human factual sleep/rest observations.

Core concepts:

- sleep_observation_id
- resident_id
- observed_at
- observation_type
- observable_facts
- baseline_change
- state
- recorded_by
- verified_by
- verified_at
- amendment_of
- amendment_reason

Observation is not diagnosis.

## 3. night_monitoring_checks

Human night monitoring records.

Core concepts:

- night_check_id
- resident_id
- sleep_care_plan_id
- scheduled_at
- performed_at
- observation
- resident_state
- mobility_observation
- environmental_observation
- performed_by
- state

Night monitoring must not unnecessarily disturb sleep.

## 4. sleep_rest_events

Observable sleep/rest related events.

Examples:

- repeated waking
- prolonged wakefulness observation
- night restlessness
- sleep-wake reversal observation
- night wandering observation
- night-time distress observation

Core concepts:

- sleep_rest_event_id
- resident_id
- event_type
- observed_at
- observable_facts
- location
- state
- owner_id
- assigned_at
- acknowledged_at
- resolved_at

Lifecycle:

OPEN
-> ASSIGNED
-> ACKNOWLEDGED
-> RESPONDING
-> RESOLVED
-> CLOSED

## 5. night_support_responses

Append-only human support response.

Examples:

- reassurance
- environmental adjustment
- toileting assistance
- hydration offer where permitted
- comfort support
- orientation support

Core concepts:

- response_id
- resident_id
- sleep_rest_event_id
- response_type
- response_notes
- performed_by
- performed_at
- state
- verified_by
- verified_at

No medication mutation is permitted.

## 6. sleep_safety_alerts

Human-confirmed or system-advisory safety concern record.

Examples:

- repeated night waking pattern
- increased night mobility
- possible fall-risk concern
- significant change from known baseline

AI-generated detections remain advisory and may not become
official human-confirmed findings without human review.

Core concepts:

- alert_id
- resident_id
- source_type
- source_id
- alert_type
- state
- created_by
- acknowledged_by
- reviewed_by
- resolved_by

## 7. sleep_escalations

Human escalation workflow.

Core concepts:

- sleep_escalation_id
- resident_id
- source_type
- source_id
- reason
- state
- reviewer_id
- assigned_by
- accepted_by
- resolved_by
- resolution_notes

Lifecycle:

OPEN
-> ASSIGNED
-> ACCEPTED
-> RESOLVED

## 8. sleep_audit

Append-only audit history.

Core concepts:

- audit_id
- resident_id
- entity_type
- entity_id
- event_type
- actor_id
- actor_role
- sequence_no
- event_payload
- created_at

Requirements:

- same transaction as business mutation
- attributable actor
- append-only
- unique sequence per entity
- failed mutation = zero audit
- losing concurrent mutation = zero audit
