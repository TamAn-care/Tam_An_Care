### Interpretation rule

A Phase 1 gap is an evidence-based candidate for Phase 2 design.

A gap is **not automatically permission to modify code**.

In particular:

- Missing controller-file actor-header evidence must be traced through guards, interceptors, authorization services and global application behavior.
- A backend domain without a dedicated frontend route may be intentionally consumed by Operational Care, Resident Care View, Dashboard or cross-domain integration.
- Audit persistence does not imply that every audit table requires a dedicated UI.
- No new request fields, routes, roles or database structures may be invented.

### Gap matrix


#### GAP-P1-004 — CRITICAL — Security

**Finding:** Mutation controllers exist without controller-file actor-header evidence

**Classification:** `SECURITY_REVIEW_REQUIRED`

**Recommended Phase 2 action:** Do not patch automatically. Phase 2 must trace guards, interceptors, authorization services and handler semantics for every candidate before deciding whether a real fail-closed gap exists.


#### GAP-P1-001 — HIGH — API Contract

**Finding:** Some controller route expressions are not statically resolved by the Phase 1 audit parser

**Classification:** `AUDIT_CONTRACT_GAP`

**Recommended Phase 2 action:** Phase 2 must resolve these routes from source imports/constants/decorator semantics before implementation.


#### GAP-P1-002 — HIGH — Frontend Coverage

**Finding:** Backend domains with public routes have no direct frontend evidence

**Classification:** `COVERAGE_GAP_CANDIDATE`

**Recommended Phase 2 action:** Phase 2 must classify each as intentionally backend-only, dashboard-integrated, or requiring UI/workflow exposure.


#### GAP-P1-006 — HIGH — Care Domain UX

**Finding:** Specialized senior-care domains expose backend operations without direct frontend evidence

**Classification:** `CARE_DOMAIN_UI_GAP_CANDIDATE`

**Recommended Phase 2 action:** Phase 2 must determine whether these belong inside Operational Care, resident care view, or dedicated workflow screens; do not create screens blindly.


#### GAP-P1-003 — MEDIUM — Audit Visibility

**Finding:** Extensive audit persistence exists but no frontend audit visibility evidence was detected

**Classification:** `OBSERVABILITY_GAP_CANDIDATE`

**Recommended Phase 2 action:** Phase 2 should determine which audit/history views are operationally required for supervisors and governance roles.


## Phase 2 design priorities

Phase 2 must:

1. Resolve every remaining ambiguous API/security contract before implementation.
2. Distinguish true gaps from intentionally backend-only support modules.
3. Preserve the V7.6/V7.7 architecture instead of redesigning it.
4. Prioritize operational workflow completeness over adding disconnected screens.
5. Preserve fail-closed actor security and anti-impersonation.
6. Define which audit/history evidence must be visible to supervisors.
7. Define responsive acceptance for any UI changed in V7.7.
8. Keep schema unchanged unless a dedicated isolated migration gate proves a schema change is necessary.
9. Produce an explicit Phase 2 implementation scope and exclusion list.
10. Require isolated functional acceptance before any production promotion.
