# Tam An Care V7.4.3
# STEP 8C.A
# Operational Dashboard / Staff Work Queue / Resident Navigation

## 1. Purpose

Step 8C introduces a read-only operational coordination layer above the
Step 8B Unified Resident Care View.

Its purpose is to help authorized staff answer:

- Which residents require attention?
- Which assigned or scheduled care work should be reviewed?
- Which existing clinical records may require human review?
- Which medication operational records require awareness?
- Which incidents remain operationally open?
- How can staff navigate quickly to the resident care view?

Step 8C is not a new source of truth.

## 2. Architecture

Authoritative source domains
    |
    v
Step 8A Cross-Domain Integration
    |
    v
Step 8B Unified Resident Care View
    |

Step 8C Operational Dashboard / Work Queue
    |
    v
Future UI

Step 8C must not bypass Step 8B to invent independent resident semantics.

## 3. Read-Only Rule

The dashboard is read-only.

No dashboard endpoint may directly:

- complete care tasks
- assign care tasks
- modify care plans
- create clinical observations
- verify clinical observations
- prescribe medication
- hold medication
- administer medication
- change medication orders
- resolve incidents
- close incidents
- perform disciplinary action
- trigger hospital transfer
- perform autonomous clinical action

Mutation must remain in the authoritative domain workflow.

## 4. No Duplicate Persistence

Step 8C must initially be computed.

Do not introduce:

- dashboard table
- staff_work_queue table
- operational_queue table
- attention_queue table
- resident_attention table
- materialized operational dashboard

unless a later performance gate proves persistence is necessary.

## 6. Dashboard Summary

summary may include computed counts such as:

- visibleResidents
- openTasks
- dueTasks
- missedTasks
- clinicalItemsForReview
- medicationItemsForAwareness
- openIncidents

Counts are presentation metadata.

Counts must not be treated as new authoritative business records.

## 7. Resident Navigation

residents[] should provide a compact navigation projection.

Possible fields:

- residentId
- residentCode
- displayName
- room
- bed
- careLevel
- activeStatus

Navigation must link to:

GET /api/operations/residents/:residentId/care-view

Resident navigation must respect the same authorization policy as the
underlying resident view.

## 8. Work Queue

workQueue[] is a computed projection primarily from care_tasks.

Possible fields:

- residentId
- careTaskId
- taskCode
- title
- taskCategory
- status
- priority
- scheduledAt
- dueAt
- assignedTo
- assignedRole

The queue must preserve source identifiers.

The dashboard does not own task lifecycle.

## 9. Attention Items

attention[] may reference existing source facts requiring human review.

Possible categories:

TASK
CLINICAL
MEDICATION
INCIDENT

Each attention item should contain:

- type
- residentId
- sourceRecordId
- sourceStatus
- sourceTimestamp
- displayReason
- provenance

displayReason must describe existing source facts.

It must not invent a medical diagnosis.

## 10. Task Attention Semantics

Task attention may use existing explicit source state and time information.

Examples of safe presentation categories:

- scheduled
- due
- overdue
- missed
- assigned
- active

The implementation must derive these only from approved source fields and
approved time semantics.

It must not automatically change task status.

## 11. Clinical Attention Semantics

Clinical attention may expose an existing abnormal flag or unverified record
for human review.

Step 8C must not invent new clinical thresholds.

No:

- diagnosis
- severity inference
- treatment recommendation
- autonomous escalation

unless separately governed by a later approved clinical/AI workflow.

## 12. Medication Attention Semantics

Medication operational awareness may use existing fields such as:

- order status
- high-risk flag
- double-check-required flag
- administration status
- scheduled time
- missed/refused/held state

The dashboard must not interpret this as authority to prescribe, hold,
administer, discontinue, or change medication.

## 13. Incident Attention Semantics

Incident awareness may use existing:

- status
- severity field where already recorded
- assignment
- acknowledgement
- resolution / closure state

Step 8C must not resolve, close, assign or alter incident severity.

## 14. Deterministic Ordering

Dashboard ordering must be deterministic.

For work items, use explicit source timestamps and stable source IDs as
tie-breakers.

No list may depend on physical database row order.

Priority labels must not silently override explicit source workflow state.

## 15. Availability Semantics

Dashboard sections must distinguish:

AVAILABLE
EMPTY
UNAVAILABLE

EMPTY:
the read succeeded with no relevant records.

UNAVAILABLE:
the source could not be safely read.

Do not convert source errors to empty queues.

## 16. Partial Failure

Failure of one secondary dashboard component must not create a misleading
empty dashboard.

Where safe:

- resident navigation may remain available;
- unaffected sections remain available;
- failed sections become UNAVAILABLE.

## 17. Provenance

Every dashboard item must retain enough provenance to navigate back to its
authoritative record.

Examples:

TASK -> care_tasks
CLINICAL -> clinical_observations
MEDICATION_ORDER -> medication_orders
MEDICATION_ADMINISTRATION -> medication_administrations
INCIDENT -> incidents

Computed dashboard metadata must be labeled computed.

## 18. Role Visibility

Step 8C must reuse server-side access policy.

Current proven role gate:

CAREGIVER
NURSE
SUPERVISOR

Role-specific visibility must not be broader than Step 8B.

CAREGIVER:
operationally necessary, redacted data only.

NURSE:
clinical operational read where authorized.

SUPERVISOR:
supervisory operational read where authorized.

AI and SYSTEM:
must not obtain human role authority.

## 19. Resident Assignment Scope

Full resident assignment scope is not yet proven.

Current known security:

ROLE_GATE_ONLY

Step 8C must not pretend that resident-level assignment authorization exists.

A later security gate must discover and formalize:

- facility scope
- team scope
- shift scope
- resident assignment scope

before claiming resident-specific scope enforcement.

## 20. Security Transparency

Until full assignment scope exists, backend metadata should not claim more
than ROLE_GATE_ONLY.

Do not hide this limitation in the UI contract.

## 21. Performance Contract

Dashboard is operational and must remain bounded.

Required:

- no N+1 query pattern
- no per-resident query loop
- no per-task follow-up query loop
- no audit-history bulk load
- no unbounded historical retrieval
- bounded resident list
- bounded work queue
- bounded attention list
- stateless computation
- no mandatory cache for correctness

Query complexity should remain O(number of fixed source domains), not
O(number of returned residents or records).

## 22. Dashboard Limits

Exact limits are deferred to Step 8C.B.

Step 8C.B must define:

- maximum visible residents in compact overview
- maximum work queue items
- maximum attention items
- ordering
- tie-breakers
- overflow/navigation behavior

The dashboard must not silently truncate without exposing limits.

## 23. Time Semantics

Step 8C may compare source timestamps with generatedAt for operational
presentation.

It must not create medical thresholds.

Terms such as overdue should only be used where due_at or an equivalent
approved operational deadline exists.

Do not infer overdue from unrelated timestamps.

## 24. Smooth UI Contract

Backend should provide deterministic sections allowing the future UI to
render independently:

- summary
- resident navigation
- work queue
- attention panel

UI should distinguish:

loading
available
empty
unavailable

UI must not reconstruct backend authorization.

## 25. Navigation Contract

Dashboard links may navigate to:

GET /api/operations/residents/:residentId/care-view

Future mutation actions must navigate to authoritative workflows rather than
mutating through the dashboard read endpoint.

## 26. HTTP Boundary

Operational dashboard endpoint must be GET-only.

Preferred future endpoint:

GET /api/operations/dashboard

No:

POST
PUT
PATCH
DELETE

for the dashboard read surface.

## 27. AI Boundary

AI is not required for Step 8C.

If introduced later, AI may:

- summarize authorized dashboard information
- organize existing items
- suggest human review priority

AI may not:

- alter task status
- diagnose
- prescribe
- administer medication
- resolve incidents
- bypass redaction
- expand permissions
- create official source-domain records

## 29. Non-Goals of Step 8C.A

Step 8C.A does not:

- modify source
- modify schema
- create database tables
- create dashboard persistence
- build Docker image
- replace runtime
- modify production
- implement UI
- implement workflow mutation
- implement resident assignment scope
- introduce autonomous AI action

## 30. Gate

Step 8C.A passes only if:

- Step 8B locked baseline is intact;
- Step 8B remains read-only;
- no dashboard persistence exists;
- source-domain authority is preserved;
- dashboard mutation is denied;
- role visibility is defined;
- assignment-scope limitation is explicit;
- attention semantics do not create diagnosis or authority;
- deterministic ordering is required;
- availability and provenance are explicit;
- bounded performance is required;
- future UI/backend boundary is defined.
