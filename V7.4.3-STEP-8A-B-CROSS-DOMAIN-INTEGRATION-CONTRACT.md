# TAM AN CARE V7.4.3
# STEP 8A.B — CROSS-DOMAIN INTEGRATION CONTRACT

STATUS: DESIGN CONTRACT
IMPLEMENTATION: NOT STARTED

---

## 1. PURPOSE

Step 8A introduces the cross-domain integration layer for
Tâm An Care V7.4.3.

The integration layer SHALL:

- provide resident-centric aggregation;
- normalize existing domain summaries;
- expose operational visibility;
- preserve source-domain ownership;
- preserve source-domain audit history;
- preserve human clinical authority;
- expose AI signals only as advisory information;
- support future timeline, handover and supervisor views.

The integration layer SHALL NOT become a new clinical
system-of-record.

---

## 2. ARCHITECTURAL PRINCIPLE

SOURCE DOMAIN OWNS TRUTH.

INTEGRATION LAYER OWNS VIEW.

HUMAN OWNS CLINICAL DECISION.

AI OWNS ADVISORY SIGNAL ONLY.

No cross-domain component may silently mutate a source domain.

## 4. SYSTEM OF RECORD RULE

Every clinical or operational fact SHALL retain:

- sourceDomain
- sourceEntityType
- sourceEntityId
- residentId where applicable
- source timestamp
- source status
- source audit reference where available

The integration layer SHALL NOT fabricate source state.

If source data is unavailable, the integration result SHALL
represent the state as unavailable/unknown rather than infer
a clinical fact.

---

## 5. CROSS-DOMAIN READ CONTRACT

The integration layer MAY:

1. Query existing domain state.
2. Query existing domain summaries.
3. Aggregate resident-related information.
4. Normalize timestamps and display metadata.
5. Classify information for operational presentation.
6. Reference warning/escalation state.
7. Reference pending human-review state.
8. Reference advisory AI signals.
9. Produce derived NON-CLINICAL presentation metadata.

Examples of allowed derived metadata:

- display category
- domain label
- chronology
- operational priority presentation
- unresolved-item count
- pending-review count
- source freshness
- source availability

Derived metadata MUST NOT be represented as a new
clinical diagnosis or treatment decision.

---

CROSS-DOMAIN DIRECT WRITE = DENIED.

Step 8A SHALL NOT directly write into:

- medication records

- incidents

- safeguarding records
- infection-control records
- fall/mobility records
- nutrition/hydration records
- rehabilitation records
- behavioral/cognitive records

## 10. AI BOUNDARY

AI MAY:

- detect patterns;
- summarize information;
- rank advisory attention;
- identify possible anomalies;
- generate advisory explanations;
- support workload visibility;
- support quality-management review.

AI SHALL NOT:

- diagnose;
- prescribe;
- administer medication;
- alter medication;
- order restraint;
- order hospital transfer;
- close clinical incidents;
- resolve safeguarding matters;
- override human review;
- silently mutate clinical records.

autonomousClinicalAction = false

Human-review requirements SHALL remain enforceable.

---

## 11. AUDIT CONTRACT

Cross-domain aggregation SHALL preserve source audit
references where available.

The integration layer SHALL NOT:

- overwrite source audit events;
- resequence source audit events;
- delete source audit history;
- hide source attribution.

Future integration-owned audit events, if introduced,
MUST be append-only and limited to integration activity.

---

## 12. CONSISTENCY CONTRACT

Cross-domain views are projections of source-domain state.

Therefore:

SOURCE DOMAIN STATE > INTEGRATION PROJECTION.

If disagreement occurs:

1. Source-domain record wins.
2. Projection must be refreshed.
3. No source-domain correction may be performed silently
   by the integration layer.

---

## 13. FAILURE CONTRACT

Failure of one source domain SHALL NOT fabricate a
successful result.

Aggregation responses SHALL support partial availability.

Possible domain state:

- AVAILABLE
- EMPTY
- UNAVAILABLE
- ERROR
- STALE

Clinical absence and technical unavailability MUST NOT
be treated as equivalent.

---

## 14. SECURITY / AUTHORIZATION CONTRACT

Aggregation SHALL NOT increase actor authority.

A user who cannot access a source-domain clinical record
must not gain that access through the integration layer.

Future Step 8 implementation MUST enforce equivalent or
stricter access than the underlying domain.
