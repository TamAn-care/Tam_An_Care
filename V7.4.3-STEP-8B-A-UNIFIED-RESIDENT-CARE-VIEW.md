# Tam An Care V7.4.3
# STEP 8B.A — Unified Resident Care View / Operational Read Model

## 1. Purpose

Step 8B converts the safe Step 8A cross-domain read foundation into a
canonical operational resident-care view suitable for later UI consumption.

Step 8B does not create a second source of truth.

Source domains remain authoritative.

## 2. Architectural Rule

Source Domains
    |
    | bounded read only
    v
Step 8A Integration Layer
    |
    | canonical aggregation
    v
Step 8B Operational Read Model
    |
    v
Future UI / workflow presentation

The operational read model is computed, not independently persisted.

## 3. Source-of-Truth Ownership

Resident identity:
- residents

Care planning:
- care_plans

Operational care tasks:
- care_tasks

Clinical observations:
- clinical_observations

Medication:
- medication_orders
- medication_administrations

Incident information:
- incidents

Step 8B must not become owner of any source-domain record.

## 4. Canonical View Sections

The canonical resident view shall expose logically separated sections:

1. resident
2. carePlan
3. workQueue
4. clinical
5. medication
6. incidents
7. availability
8. provenance
9. freshness
10. authority

The presentation model may summarize source records but must preserve
traceability to their source identifiers.

## 5. Resident Header

The resident header may include:

- resident identifier
- display name
- date of birth
- gender
- room
- bed
- care level
- active status

No new resident master record shall be created.

## 6. Care Plan Section

The care-plan section should prioritize the operationally relevant plan.

It may expose:

- plan identifier
- title
- status
- effective period
- human creator / approver where available

The read model must not approve, activate, modify, or close a care plan.

## 7. Work Queue Section

Care tasks may be projected into a bounded operational list.

The projection may support later UI classification such as:

- pending
- assigned
- active
- overdue
- completed

Step 8B itself must not perform task mutation.

No hidden workflow transition is permitted.

## 8. Clinical Section

Clinical observations remain factual source records.

The read model may display recent observations and existing abnormal flags.

It must not:

- diagnose
- invent thresholds
- prescribe treatment
- change clinical status
- create autonomous clinical actions

## 9. Medication Section

Medication information is read-only.

Orders and administration records must remain distinguishable.

The view must not:

- prescribe
- discontinue
- hold
- administer
- alter dose
- alter route
- alter frequency

Medication authority remains human and source-domain controlled.

## 10. Incident Section

Incident records may be presented as bounded recent operational information.

The read model must not:

- resolve incidents
- close incidents
- assign incidents
- change severity
- create disciplinary action

## 11. Availability Semantics

Every domain section must communicate availability explicitly.

Recommended states:

AVAILABLE
EMPTY
UNAVAILABLE

AVAILABLE:
the domain read succeeded and returned data.

EMPTY:
the domain read succeeded but no records exist.

UNAVAILABLE:
the domain read failed or could not be safely resolved.

EMPTY and UNAVAILABLE must never be treated as equivalent.

## 12. Partial Failure

Failure of one non-resident domain must not automatically destroy the entire
resident overview.

Resident identity is the root existence gate.

If the resident does not exist:
- fail closed.

If a secondary domain fails:
- retain the resident overview where safe;
- mark the failed section UNAVAILABLE;
- do not fabricate an empty result.

## 13. Provenance

Every projected domain must retain explicit source provenance.

Examples:

resident -> residents
carePlan -> care_plans
workQueue -> care_tasks
clinical -> clinical_observations
medication -> medication_orders / medication_administrations
incidents -> incidents

The UI must be able to distinguish source-derived data from computed
presentation metadata.

## 14. Freshness Contract

Step 8B shall define freshness metadata without creating a persistence cache.

Freshness may be derived from:

- generatedAt
- source updated_at
- source recorded_at
- source reported_at
- source administered_at where applicable

No fabricated clinical freshness threshold is permitted.

Freshness is informational.

It is not a clinical diagnosis or automatic escalation rule.

## 15. Authority Contract

The canonical response must preserve an explicit authority boundary.

Required principles:

readOnly = true

crossDomainMutation = false

autonomousClinicalAction = false

autonomousMedicationAction = false

autonomousIncidentAction = false

AI may later summarize or prioritize information for human review.

AI must not become the official actor for source-domain mutation.

## 16. Authorization / Redaction Boundary

Step 8B.A defines the architectural requirement that future UI exposure must
respect role-based authorization.

The operational read model must not weaken existing RBAC.

Future implementation must provide a controlled place for field/section
redaction where role policy requires it.

Authorization must occur server-side.

Client-side hiding alone is not sufficient authorization.

## 17. Performance Contract

The resident view is an operational screen and must remain bounded.

Required principles:

- no N+1 query pattern
- no unbounded history retrieval
- no audit-history bulk load
- bounded records per domain
- parallel independent reads where safe
- stateless aggregation
- no mandatory cache for correctness
- no duplicate persistence

Initial implementation should reuse the Step 8A per-domain bound.

Performance optimization must not weaken source-of-truth correctness.

## 18. Smooth UI Contract

The future UI must be able to render the resident header independently from
secondary domain sections.

Secondary sections must support:

- AVAILABLE
- EMPTY
- UNAVAILABLE

A single secondary-domain failure must not produce a misleading blank
resident screen.

The backend response should be deterministic enough to prevent unnecessary
client-side reconstruction of domain semantics.

## 19. Ordering

Ordering must be deterministic.

Where source timestamps exist, recent operational records should use explicit
timestamp ordering.

No UI should depend on incidental database row order.

## 20. No Duplicate Persistence

Step 8B shall not introduce tables such as:

- unified_resident_view
- resident_overview
- operational_read_model
- resident_care_view

unless a later roadmap gate proves persistence is necessary.

The default architecture is computed read projection.

## 21. Mutation Boundary

Step 8B must not provide:

POST
PUT
PATCH
DELETE

for the unified resident care view.

Any future operational mutation must return to the authoritative source
domain through its controlled human-authorized workflow.

## 22. AI Boundary

AI may later:

- summarize existing data
- highlight information for human review
- identify trends for human review
- help navigation

AI may not:

- diagnose
- prescribe
- administer medication
- resolve incidents
- modify care plans
- complete care tasks
- create official clinical records
- perform autonomous source-domain mutation

## 23. Implementation Strategy

Preferred roadmap:

8B.A
Design + safety contract.

8B.B
Exact response DTO / mapping / RBAC / freshness / performance design.

8B.C
Controlled backend implementation.

8B.D
Acceptance, concurrency, degraded-domain behavior, regression and closure.

UI implementation begins only after the backend operational read contract is
stable.

## 24. Non-Goals

Step 8B.A does not:

- change schema
- migrate database
- create materialized views
- create cache infrastructure
- change source-domain ownership
- modify production
- implement UI
- implement mutation
- introduce autonomous AI action

## 25. Gate

Step 8B.A passes only if:

- Step 8A baseline remains locked;
- existing integration remains read-only;
- no duplicate persistence exists;
- source ownership remains unchanged;
- availability semantics are explicit;
- partial failure behavior is explicit;
- provenance is preserved;
- freshness semantics are defined;
- RBAC/redaction boundary is defined;
- performance remains bounded;
- UI/backend responsibilities are separated;
- AI/human authority remains explicit.
