# Tam An Care V7.4.3 — STEP 7I

## Care Execution / Start-Review Authorization

### 1. Objective

Define the authorization boundary for moving a Care Action:

PENDING -> IN_REVIEW

The transition represents the beginning of actual human care execution.

It must never be triggered autonomously by AI.


### 2. Core Safety Principle

A Care Action may enter IN_REVIEW only through an explicit human action.

AI may:

- detect warning patterns;
- recommend human review;
- associate warnings with residents;
- support decision-making.

AI may NOT:

- accept responsibility;
- assign itself or another person;
- start review;
- resolve a Care Action;
- reopen a Care Action;
- perform autonomous clinical action.


### 3. Preconditions

Start Review is allowed only when ALL conditions below are true:

1. Care Action exists.
2. Care Action status is PENDING.
3. Care Action has an assigned human owner.
4. actorId is present.
5. actorRole is present.
6. Actor is authorized.
7. Transition is executed atomically.
8. Audit event is created in the same transaction.


### 4. Owner Authorization

The primary authorization rule is:

actorId == careAction.assignedTo

The assigned owner may start review of their own Care Action.


### 5. Supervisor Override

A supervisor may start review on behalf of operational continuity only if:

- actorRole is an explicitly authorized supervisory role;
- actorId is present;
- Care Action already has an assigned owner;
- the action remains assigned to the existing owner;
- supervisor action is fully audited;
- override does NOT silently transfer responsibility.

Initial V7.4.3 supervisory roles:

SUPERVISOR
CARE_MANAGER

No other role receives override authority by default.


### 6. Explicitly Forbidden Cases

Start Review must be rejected when:

- Care Action does not exist;
- Care Action is unassigned;
- actorId is missing;
- actorRole is missing;
- actor is not current owner;
- actor is not an authorized supervisor;
- Care Action is already IN_REVIEW;
- Care Action is RESOLVED;
- AI/system identity attempts the transition;
- two requests attempt the same transition concurrently after one has succeeded.


### 7. State Transition

Valid:

PENDING -> IN_REVIEW

Invalid:

PENDING -> PENDING
IN_REVIEW -> IN_REVIEW
IN_REVIEW -> PENDING
RESOLVED -> IN_REVIEW through Start Review

Reopening a resolved action remains a separate explicit workflow.


### 8. Ownership Rule

Start Review must NOT:

- change assignedTo;
- change assignedRole;
- create TRANSFER history;
- silently reassign responsibility.

Responsibility remains with the accepted owner unless an explicit transfer workflow is executed.


### 9. Audit Contract

Successful Start Review produces exactly one new audit event:

REVIEW_STARTED

Expected sequence for normal workflow:

CREATED
-> ASSIGNED
-> REVIEW_STARTED

Audit must include:

- careActionId;
- residentId;
- patternId;
- actorId;
- actorRole;
- previousState;
- newState;
- deterministic eventSequence;
- timestamp.


### 10. Concurrency Contract

If two authorized requests attempt Start Review simultaneously:

- exactly one request may succeed;
- exactly one REVIEW_STARTED audit event may be created;
- final status must be IN_REVIEW;
- no duplicate audit event is allowed;
- ownership must remain unchanged.


### 11. Negative Guard Contract

The implementation must test:

- unknown action -> 404;
- unassigned action -> 400;
- missing actorId -> 400;
- missing actorRole -> 400;
- unauthorized actor -> 400 or 403;
- second Start Review -> rejected;
- Start Review on RESOLVED -> rejected;
- AI/system actor -> rejected.


### 12. Human-in-the-Loop Boundary

Responsibility acceptance and start-review remain distinct operations:

CREATE CARE ACTION
-> PENDING / UNASSIGNED

ACCEPT RESPONSIBILITY
-> PENDING / ASSIGNED

START REVIEW
-> IN_REVIEW / SAME OWNER

This separation is intentional and mandatory.


### 13. Database Scope

STEP 7I design introduces no database schema change.

Existing care_actions and care_action_audit structures are sufficient.

No new table is authorized at design stage.


### 14. Implementation Sequence

STEP 7I   — authorization design
STEP 7I.1 — authorization policy/source implementation
STEP 7I.2 — isolated build + runtime test
STEP 7I.3 — concurrency + negative regression

Only after all gates PASS may the roadmap proceed to execution/resolve authorization.


### 15. Production Boundary

V7.4.2 production remains immutable throughout STEP 7I development.

No production migration.
No production build.
No production cutover.
