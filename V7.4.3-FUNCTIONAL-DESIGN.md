# Tam An Care V7.4.3
## Functional Design Baseline

---

# 1. Objective

V7.4.3 extends the V7.4.2 Care Action foundation into
a practical human-controlled care operations workflow.

The system must connect:

Resident

→ Health Observation

→ AI Early Warning

→ Human Review

→ Care Action

→ Responsibility Assignment

→ Responsibility Acceptance

→ Care Execution

→ Resolution

→ Supervisor Review

→ Audit

AI remains advisory only.

No autonomous clinical action is permitted.

---

# 2. Resident Context

Every operational Care Action must have enough context
to identify the person receiving care.

Minimum Resident Context:

- residentId
- residentCode
- displayName
- dateOfBirth
- gender
- room
- bed
- careLevel
- activeStatus

V7.4.3 does not yet require a full Electronic Medical Record.

Resident Context is an operational identity layer.

---

# 3. Health Observation Context

An Early Warning should be traceable to observations
belonging to the same Resident.

Core observations may include:

- weight
- food/fluid intake
- sleep
- SpO2
- mobility
- blood pressure
- temperature
- pulse
- notes

The AI result must not overwrite original observations.

---

# 4. Early Warning

AI Early Warning remains advisory.

An Early Warning contains:

- residentId
- warningLevel
- confidence
- detectedPatterns
- metricsAffected
- recommendation
- humanReviewRequired
- autonomousClinicalAction=false
- createdAt

The warning itself must not assign staff automatically.

---

# 5. Human Review

A human staff member must explicitly review a warning.

Human Review records:

- reviewerId
- reviewerRole
- reviewedAt
- decision
- careNote

Possible decisions:

- NO_ACTION_REQUIRED
- MONITOR
- CREATE_CARE_ACTION
- ESCALATE

The AI does not make this decision.

---

# 6. Care Action

A Care Action is the operational response to a reviewed
warning or another human-identified care need.

Required context:

- careActionId
- residentId
- sourceType
- sourceId
- priority
- status
- assignedTo
- assignedRole
- dueAt
- createdAt

Source types should support:

- AI_WARNING
- MANUAL
- CARE_PLAN
- INCIDENT

---

# 7. Care Action Lifecycle

Target lifecycle:

UNASSIGNED
    ↓
ASSIGNED
    ↓
ACCEPTED
    ↓
IN_PROGRESS
    ↓
COMPLETED
    ↓
REVIEWED
    ↓
CLOSED

Exception paths:

ASSIGNED
    → TRANSFERRED

ACCEPTED
    → TRANSFERRED

IN_PROGRESS
    → TRANSFERRED

COMPLETED
    → REOPENED

REOPENED
    → IN_PROGRESS

The existing V7.4.2 PENDING / IN_REVIEW / RESOLVED
state machine must not be deleted during V7.4.3 development.

A compatibility strategy must be defined before migration.

---

# 8. Responsibility Acceptance

Assignment alone is not sufficient.

The person receiving responsibility should explicitly
accept responsibility.

Acceptance records:

- careActionId
- assignedTo
- acceptedBy
- acceptedAt
- actorRole

This supports accountability in real care operations.

---

# 9. Transfer Responsibility

Transfer must preserve full history.

A transfer records:

- from staff
- to staff
- reason
- actor
- actorRole
- transferredAt

The original assignment history must remain immutable.

---

# 10. Execution

Care staff should be able to record:

- startedAt
- actionTaken
- careNote
- observations
- completedAt

The system records what the human did.

AI must not mark a Care Action complete.

---

# 11. Supervisor Review

Selected completed Care Actions should support
supervisor review.

Supervisor review may record:

- reviewerId
- reviewerRole
- reviewedAt
- result
- comment

Possible results:

- APPROVED
- FOLLOW_UP_REQUIRED
- REOPENED

---

# 12. Operational Dashboard

The dashboard should provide:

## Alerts

- new high-risk warnings
- warnings waiting for human review

## Care Actions

- unassigned
- assigned
- accepted
- in progress
- overdue
- completed
- reopened

## Staff Responsibility

- actions by caregiver
- overdue workload
- transfers
- pending acceptance

## Resident Context

- active warnings
- open actions
- recent completed actions

---

# 13. Overdue Logic

A Care Action is overdue when:

- dueAt exists
- current time > dueAt
- action is not completed/closed

Overdue status is calculated.

It must not modify the clinical state automatically.

---

# 14. Human-in-the-loop Rules

The following require a human actor:

- review warning
- create Care Action from warning
- assign
- accept responsibility
- transfer
- start action
- complete action
- resolve
- reopen
- supervisor review

Every human command must capture:

- actorId
- actorRole
- timestamp

---

# 15. AI Governance Rules

Preserve all existing controls:

- kill switch
- risk classification
- human review requirement
- auditability
- no autonomous clinical action

AI may:

- detect
- summarize
- recommend
- prioritize

AI may not:

- prescribe
- assign staff automatically
- mark care completed
- close a Care Action
- override a human decision

---

# 16. Audit Requirements

Audit events must remain append-only.

Minimum events:

- WARNING_REVIEWED
- CARE_ACTION_CREATED
- ASSIGNED
- ACCEPTED
- TRANSFERRED
- STARTED
- COMPLETED
- REVIEWED
- REOPENED
- CLOSED

Audit records must include:

- eventSequence
- actorId
- actorRole
- previousState
- newState
- createdAt

---

# 17. Safety Rule

V7.4.3 development must never use the V7.4.2
production database.

Development DB:

taman_care_v743_dev

Production DB:

taman_care

These databases must remain separated.

---

# 18. Compatibility Requirement

Before changing V7.4.2 Care Action status values,
V7.4.3 must define a compatibility mapping.

Current V7.4.2:

PENDING
IN_REVIEW
RESOLVED

Target operational model:

UNASSIGNED
ASSIGNED
ACCEPTED
IN_PROGRESS
COMPLETED
REVIEWED
CLOSED

No destructive status migration is allowed during
early V7.4.3 development.

---

V7.4.3 is experimental until formally promoted through
regression, freeze and controlled cutover.
