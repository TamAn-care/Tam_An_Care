# TAM AN CARE V7.5
## STEP 9A — SCOPE LOCK

Status: LOCKED

---

# 1. In scope

V7.5 SHALL deliver the operational application layer above V7.4.3.

In scope:

- frontend architecture
- design system
- application shell
- role-based navigation
- resident operational UI
- operational dashboard UI
- canonical staff/access administration UI
- care operations workspace
- extended care domain presentation
- controlled AI assistance UI
- responsive web/PWA
- UX hardening
- end-to-end acceptance
- macOS application packaging
- Windows packaging after macOS acceptance
- release freeze

---

# 2. Protected V7.4.3 baseline

The following V7.4.3 capabilities are treated as accepted baseline:

- operational dashboard
- canonical resident authorization
- access administration
- canonical human staff identity
- fail-closed authority boundaries
- rollback chain
- accepted database schema

They MUST be reused rather than rewritten unless an explicit defect is proven.

---

# 3. Out of scope for early V7.5

The following are NOT allowed during early UI implementation unless separately
approved:

- broad backend redesign
- mass database migration
- destructive schema rewrite
- production cutover
- removal of rollback containers
- replacement of canonical identity model
- replacement of canonical resident authorization model
- uncontrolled AI autonomy
- native mobile redesign before responsive/PWA acceptance

---

# 4. Core UI roles

Initial operational UI roles:

- CAREGIVER
- NURSE
- SUPERVISOR

CARE_MANAGER may be designed where appropriate, but must not bypass canonical
backend authority.

AI and SYSTEM are not human UI actors.

---

# 5. Core navigation target

Target application navigation:

- Dashboard
- Residents
- Care Operations
- Medication
- Clinical
- Incidents
- Staff & Access
- AI Assistance
- Reports / Monitoring
- Settings / System Status

Final visibility is role-based.

---

# 6. First usable vertical slice

The first frontend vertical slice SHALL be:

Login / Actor Context
-> Application Shell
-> Operational Dashboard
-> Resident List
-> Resident Care View
-> Staff / Access Administration

This slice must be accepted before broad domain UI expansion.

---

# 7. UX policy

UI SHALL be:

- Vietnamese-first
- simple enough for daily care-center operations
- desktop-first but responsive
- readable for non-technical users
- consistent in terminology
- explicit about destructive actions
- explicit about authorization denial
- safe under disconnected/error states

---

# 8. API integration policy

Frontend SHALL:

- consume existing V7.4.3 APIs first
- use a shared API client
- centralize actor/session headers
- centralize error handling
- avoid duplicated authorization logic in components
- treat backend as authority source
- never infer permissions solely from hidden UI controls

---

# 9. Data safety policy

UI SHALL NOT:

- silently mutate records
- bypass backend RBAC
- bypass canonical staff identity
- bypass resident authorization
- use generic destructive PATCH/DELETE behavior where backend does not support it
- fabricate success when backend returns failure

---

# 10. Acceptance philosophy

Every frontend feature must pass:

1. static/build validation
2. isolated runtime validation
3. API contract validation
4. RBAC validation
5. responsive validation
6. regression validation
7. controlled cutover
8. active acceptance
9. closure

---

# 11. V7.5 architectural principle

V7.5 is an APPLICATION COMPLETION release.

The default decision is:

USE EXISTING BACKEND
BEFORE
ADDING NEW BACKEND.

New backend work requires evidence that an accepted user workflow cannot be
implemented safely using the current contract.
