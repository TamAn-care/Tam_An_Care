# Step 7T — Canonical Data Model

The persistence gate will implement exactly eight domain tables.

## 1. cognitive_observations

Purpose:
Human-recorded observations of cognition, orientation, memory,
communication or meaningful change from known baseline.

Key concepts:
- observation_id
- resident_id
- observation_type
- observed_at
- observable_facts
- baseline_change
- recorded_by
- verification_state
- verified_by
- verified_at
- created_at
- updated_at

Official observations describe facts and do not constitute diagnosis.

## 2. behavioral_support_plans

Purpose:
Human-authored individualized support strategy.

Key concepts:
- support_plan_id
- resident_id
- status
- known_preferences
- known_triggers
- communication_approach
- reassurance_strategy
- environmental_support
- mobility_or_activity_support
- owner_id
- reviewer_id
- activated_at
- retired_at
- created_at
- updated_at

Support strategies are non-pharmacological care-support records.
They are not medication orders or clinical prescriptions.

## 3. behavioral_episodes

Purpose:
Record an observable behavioral episode.

Key concepts:
- episode_id
- resident_id
- episode_type
- observed_at
- location
- antecedent_observation
- observable_behavior
- immediate_safety_context
- state
- owner_id
- created_by
- resolved_by
- resolved_at
- created_at
- updated_at

## 4. wandering_events

Purpose:
Record wandering, exit-seeking or confirmed elopement-related events.

Key concepts:
- wandering_event_id
- resident_id
- episode_id
- event_type
- observed_at
- last_known_location
- found_location
- state
- owner_id
- acknowledged_by
- resolved_by
- resolved_at
- created_at
- updated_at

A wandering event does not itself authorize restraint,
confinement, medication or emergency transfer.

## 5. behavioral_responses

Purpose:
Append-only human documentation of support responses.

Key concepts:
- response_id
- resident_id
- episode_id
- response_type
- response_notes
- performed_by
- performed_at
- verification_state
- verified_by
- verified_at
- created_at

## 6. behavioral_escalations

Purpose:
Human-created escalation for review.

Key concepts:
- escalation_id
- resident_id
- episode_id
- reason
- state
- reviewer_id
- assigned_by
- accepted_by
- resolved_by
- resolution_notes
- created_at
- updated_at
- resolved_at

## 7. behavioral_post_reviews

Purpose:
Post-event human review and learning.

Key concepts:
- post_review_id
- resident_id
- episode_id
- review_notes
- contributing_factors
- follow_up_recommendation
- reviewer_id
- verification_state
- verified_at
- created_at

## 8. behavioral_audit

Purpose:
Append-only attributable audit history.

Key concepts:
- audit_id
- resident_id
- entity_type
- entity_id
- event_type
- actor_id
- actor_role
- sequence_no
- event_payload
- created_at

Audit requirements:
- append-only
- attributable human actor for official mutation
- same transaction as business mutation
- unique sequence within entity history
- failed mutation = zero audit
- losing concurrent mutation = zero audit
