2. D2 CANONICAL ENTITY CONTRACT
======================================================================

ENTITY: inventory_items
PURPOSE:
  Canonical inventory catalogue.

IDENTITY:
  inventory_item_id text PRIMARY KEY
  code text UNIQUE NOT NULL
  display_name_vi text NOT NULL

ATTRIBUTES:
  category text NOT NULL
  base_unit text NOT NULL
  active boolean NOT NULL DEFAULT true
  created_at timestamptz NOT NULL DEFAULT now()
  updated_at timestamptz NOT NULL DEFAULT now()

RULES:
  -> authoritative stock balance MUST NOT be stored here
  -> code immutable after creation
  -> no hard DELETE after referenced
  -> deactivate through active=false
  -> base_unit is canonical inventory accounting unit


ENTITY: inventory_lots
PURPOSE:
  Lot/batch/expiry/procurement traceability.

IDENTITY:
  inventory_lot_id text PRIMARY KEY

RELATION:
  inventory_item_id -> inventory_items.inventory_item_id

ATTRIBUTES:
  lot_code text
  received_at timestamptz
  expiry_date date
  supplier_reference text
  note text
  status text NOT NULL
  created_at timestamptz NOT NULL DEFAULT now()

RULES:
  -> lot belongs to exactly one inventory item
  -> expiry may be NULL for non-expiring items
  -> lot identity cannot migrate between items
  -> stock balance MUST NOT be authoritative here
  -> closed/exhausted lot history preserved


ENTITY: inventory_transactions
PURPOSE:
  Authoritative append-only inventory ledger.

IDENTITY:
  inventory_transaction_id text PRIMARY KEY

RELATIONS:
  inventory_item_id -> inventory_items.inventory_item_id
  inventory_lot_id -> inventory_lots.inventory_lot_id OPTIONAL
  performed_by -> staff_actors.actor_id

TRANSACTION TYPES:
  RECEIPT
  ISSUE
  ADJUSTMENT_IN
  ADJUSTMENT_OUT
  RETURN_IN
  RETURN_OUT

ATTRIBUTES:
  transaction_type text NOT NULL
  quantity numeric NOT NULL CHECK quantity > 0
  unit text NOT NULL
  occurred_at timestamptz NOT NULL
  performed_by text NOT NULL
  performed_by_role text NOT NULL
  source_domain text NOT NULL
  source_entity_type text
  source_entity_id text
  reason_code text
  note text
  created_at timestamptz NOT NULL DEFAULT now()

RULES:
  -> append-only
  -> no UPDATE of authoritative historical movement
  -> no DELETE
  -> correction uses compensating transaction
  -> authoritative stock =
       signed SUM(inventory_transactions.quantity)
  -> cached/projected balance is non-authoritative only
  -> transaction unit must match canonical item base_unit
     unless an explicit future conversion contract exists
  -> AI/System cannot independently create authoritative movement
  -> source tuple supports idempotency


ENTITY: resident_consumption_events
PURPOSE:
  Attribute consumed inventory to a resident.

IDENTITY:
  resident_consumption_event_id text PRIMARY KEY

RELATIONS:
  resident_id -> residents.resident_id
  inventory_item_id -> inventory_items.inventory_item_id
  inventory_lot_id -> inventory_lots.inventory_lot_id OPTIONAL
  inventory_transaction_id
      -> inventory_transactions.inventory_transaction_id
  work_event_id
      -> operational_work_events.work_event_id OPTIONAL
  recorded_by -> staff_actors.actor_id

ATTRIBUTES:
  quantity numeric NOT NULL CHECK quantity > 0
  unit text NOT NULL
  occurred_at timestamptz NOT NULL
  recorded_by text NOT NULL
  recorded_by_role text NOT NULL
  source_domain text NOT NULL
  source_entity_type text
  source_entity_id text
  note text
  created_at timestamptz NOT NULL DEFAULT now()

RULES:
  -> resident consumption is NOT inventory ledger
  -> every inventory-affecting resident consumption
     MUST reference exactly one inventory transaction
  -> transaction must represent an outbound movement
  -> item identity must agree with linked transaction
  -> lot identity must agree when lot is present
  -> quantity/unit must agree with linked transaction
     for one-to-one consumption transactions
  -> Work Event link optional
  -> Work Event may be linked only when its
     work_event_type.inventory_link_allowed=true
  -> resident identity must agree with linked Work Event
     when Work Event is resident-related
  -> append-only evidence
  -> correction uses explicit reversal/replacement flow,
     never silent history mutation

3. SEPARATION-OF-CONCERNS CONTRACT
======================================================================

WORK EVENT
  = who performed operational care work

INVENTORY TRANSACTION
  = what physically entered or left inventory

RESIDENT CONSUMPTION
  = which resident received/consumed inventory

Therefore:

  Work Event != Inventory Transaction
  Inventory Transaction != Resident Consumption
  Work Event != Resident Consumption

But they MAY be linked in one controlled transaction.

FORBIDDEN:
  -> deriving authoritative stock from Work Events
  -> deriving authoritative stock from Resident Consumption alone
  -> storing an independent mutable stock balance as source of truth
  -> silently changing historical inventory movements
  -> treating medication administration as generic inventory
     without an explicit later medication-inventory bridge contract

5. IDEMPOTENCY CONTRACT
======================================================================

Canonical idempotency tuple:

  source_domain
  source_entity_type
  source_entity_id

For inventory transactions:
  duplicate authoritative stock movement from the same
  source event MUST be prevented.

For resident consumption:
  duplicate resident attribution from the same source
  event MUST be prevented.

Where a single source entity can legitimately create
multiple item movements, inventory_item_id and/or
inventory_lot_id MUST participate in the uniqueness key.


======================================================================
6. TRANSACTIONAL ATOMICITY CONTRACT
======================================================================

For inventory-affecting resident consumption:

ONE DATABASE TRANSACTION MUST contain:

  1. validate actor
  2. validate resident
  3. validate inventory item
  4. validate lot when supplied
  5. validate available stock under later stock rule
  6. create authoritative inventory transaction
  7. create resident consumption event
  8. link Work Event when applicable
  9. create required append-only audit evidence
 10. COMMIT

Any failure:
  -> ROLLBACK all steps.

Projection/helper services:
  -> may accept caller transaction client
  -> must not commit/rollback caller transaction independently.

7. BALANCE CONTRACT
======================================================================

SIGNED LEDGER SEMANTICS:

POSITIVE:
  RECEIPT
  ADJUSTMENT_IN
  RETURN_IN

NEGATIVE:
  ISSUE
  ADJUSTMENT_OUT
  RETURN_OUT

AUTHORITATIVE BALANCE:
  SUM(signed quantity)

by:
  inventory_item_id

and where required:
  inventory_item_id + inventory_lot_id

NO STORED AUTHORITATIVE BALANCE COLUMN.

Future optimization may introduce:
  balance projection
  aggregate table
  cache

but only when:
  -> reconstructable from ledger
  -> explicitly non-authoritative
  -> reconciliation is possible.


======================================================================
8. NEGATIVE-STOCK CONTRACT
======================================================================

DEFAULT OPS-2 CONTRACT:

  NEGATIVE AUTHORITATIVE STOCK = FORBIDDEN

An outbound transaction must not reduce authoritative
available stock below zero.

Concurrency protection is REQUIRED.

Implementation design must use a database-safe mechanism
so two concurrent issues cannot both consume the same
remaining stock.

Exact SQL locking strategy is deferred to migration /
service implementation review.


======================================================================
9. LOT / EXPIRY CONTRACT
======================================================================

If item is lot-controlled:
  -> outbound transaction must reference a lot.

If item is not lot-controlled:
  -> lot may be NULL.

Expired lot:
  -> normal resident issue forbidden.

Expiry warning:
  -> later dashboard/report concern.

Lot balance:
  -> derived from inventory ledger.
  -> never authoritative mutable field.


======================================================================
10. AUDIT CONTRACT
======================================================================

Inventory movement history itself is append-only evidence.

Dedicated audit is required only for metadata/configuration
changes or governance actions not fully represented by the
ledger.

Candidate later audit entities:

  inventory_item_audit
  inventory_lot_audit

DO NOT create them yet.

D2 explicitly forbids inventing an additional transaction
audit table unless implementation discovery proves a
governance gap not already represented by immutable ledger
rows and canonical actor/source evidence.
