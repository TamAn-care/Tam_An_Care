# Tam An Care V7.4.3
# Step 8A.E1 — Exact Read Adapter Contract

## 1. Purpose

Define the exact implementation boundary for Step 8A.E.

Step 8A.E SHALL implement a minimal resident-centric
cross-domain read model.

It SHALL NOT create cross-domain mutation authority.

It SHALL NOT alter existing domain lifecycle ownership.

It SHALL NOT change database schema.

It SHALL NOT create autonomous clinical authority.

---

## 2. Architectural invariant

Integration layer:

READS domain-owned information.

Integration layer:

DOES NOT WRITE domain-owned information.

All authoritative mutations remain inside
their owning domain.

No integration component may call:

- mutate()
- mutateAdministration()
- report()
- createDraft()
- createPlanned()
- authorization mutation paths
- lifecycle transition commands
- any POST/PUT/PATCH/DELETE controller path

---

## 3. Wave-1 domain contract

### Residents

Status:

EXISTING READ CONTRACT.

Approved source:

ResidentService.list()

ResidentService.getById(residentId)

Integration use:

Resident identity/context anchor.

No new resident persistence logic permitted.

---

### Care Plans

EXISTING SERVICE READ CONTRACT.

Approved source:

CarePlanService.listForResident(residentId)

Optional detail:

CarePlanService.get(carePlanId)

Integration use:

Resident care-plan read projection.

No care-plan mutation permitted.

---

### Care Tasks

Status:

EXISTING SERVICE READ CONTRACT.

Approved source:

CareTaskService.listForResident(residentId)

Optional detail:

CareTaskService.get(careTaskId)

Integration use:

Resident care-task read projection.

No care-task mutation permitted.

---

### Clinical Observations

Status:

ADAPTER_REQUIRED

Current domain implementation is mutation-oriented.

Step 8A.E SHALL NOT call ClinicalService.mutate().

If adapter is required:

create a dedicated read-only resident projection
using SELECT-only database access.

Allowed data:

clinical observation records belonging to resident.

No diagnosis generation.

No clinical decision.

No escalation mutation.

No care-action creation.

No lifecycle mutation.

---

### Medication

Status:

ADAPTER_REQUIRED

Current service is administration mutation-oriented.

Step 8A.E SHALL NOT call:

MedicationService.mutateAdministration().

If adapter is required:

create a dedicated read-only resident medication
projection using SELECT-only database access.

Allowed data:

existing medication order/administration status
already recorded by medication domain.

No prescribing.

No administration.

No hold.

No cancel.

No double-check mutation.

No medication decision.

---

### Incidents

Status:

ADAPTER_REQUIRED

Current incident service is mutation-oriented.

Step 8A.E SHALL NOT call:

IncidentService.report()

IncidentService.mutate()

If adapter is required:

create a dedicated read-only resident incident
projection using SELECT-only database access.

Allowed data:

existing incidents associated with resident.

No report creation.

No triage.

No assignment.

No escalation.

No resolution.

No closure.

---

## 4. Target integration API

Step 8A.E SHALL expose ONE minimal read endpoint:

GET /api/integration/residents/:residentId/overview

This endpoint is READ ONLY.

It SHALL NOT accept mutation actions.

It SHALL NOT expose POST.

It SHALL NOT expose PUT.

It SHALL NOT expose PATCH.

It SHALL NOT expose DELETE.

---

---

## 6. Failure isolation

A domain read failure MUST NOT produce
a partial silent success.

Step 8A.E implementation SHALL use an explicit,
deterministic failure contract.

No failed domain read may trigger:

- retry mutation
- repair mutation
- fallback write
- lifecycle transition
- AI decision
- autonomous clinical action

---

## 7. Resident ownership rule

residentId is the single Wave-1 aggregation key.

All returned domain records MUST belong to
the requested resident.

No cross-resident data leakage is permitted.

---

## 8. Database rule

Step 8A.E:

NO schema.sql change.

NO new tables.

NO database migration.

NO triggers.

NO materialized views.

NO business-data writes.

Any new adapter query MUST be SELECT-only.

No SELECT FOR UPDATE.

No INSERT.

No UPDATE.

No DELETE.

---

## 9. Dependency rule

Prefer existing domain services where safe
read methods already exist.

Use dedicated read adapters only where
a safe resident read contract does not exist.

Do not modify existing mutation semantics
merely to support integration.

---

## 10. AI / human authority

Integration is informational only.

AI may consume the resulting read model later
only under separately approved AI contracts.

Step 8A.E itself grants AI ZERO mutation authority.

AI SHALL NOT:

diagnose,
prescribe,
administer medication,
change care plans,
change care tasks,
triage incidents,
close incidents,
or initiate clinical action.

---

## 11. Performance / smooth-runtime rule

Wave-1 overview should use bounded queries.

Avoid N+1 query patterns.

Do not load unbounded audit history.

Do not perform sequential per-record database calls
where a resident-scoped query is available.

Integration SHALL remain stateless.

No integration-side persistence.

---

## 12. Step 8A.E implementation scope

Permitted source changes are limited to:

1. dedicated integration module;
2. integration controller;
3. integration service;
4. minimal SELECT-only adapters where required;
5. module imports/exports required for dependency injection;
6. AppModule registration if required.

Existing domain business mutation logic
must remain semantically unchanged.

schema.sql must remain unchanged.

---

## 13. Validation required after implementation

Step 8A.E implementation MUST verify:

- build passes;
- development health HTTP 200;
- GET overview returns expected shape;
- unknown resident fails safely;
- resident isolation;
- zero POST route;
- zero mutation SQL in integration layer;
- zero SELECT FOR UPDATE;
- zero schema change;
- zero database business write during read test;
- source changes limited to approved integration scope;
- production unchanged;
- rollback image preserved.

Only after those checks pass may 8A.E
be considered complete.
