# Tam An Care V7.4.3
## STEP 7J — Care Execution / Resolution Authorization

### 1. Purpose

Define the human authorization boundary for completing a Care Action.

STEP 7J is design-only.

No application source change.
No schema change.
No database migration.
No runtime replacement.
No production change.

---

## 2. Required state

A Care Action may be resolved only when:

- status = IN_REVIEW
- assignedTo is present
- assignedRole is present
- reviewStartedAt is present
- careNote is present and non-empty
- resolutionReason is present and non-empty
- explicit human actorId is present
- explicit human actorRole is present

A PENDING Care Action cannot be resolved.

A RESOLVED Care Action cannot be resolved again.

---

## 3. Authorized actors

### Assigned Owner

The current assigned owner may resolve the Care Action.

The actorId must equal assignedTo.

The owner remains unchanged.

### SUPERVISOR

A human actor with role SUPERVISOR may resolve as an authorized override.

Supervisor override does not:

- change assignedTo
- change assignedRole
- create transfer
- take ownership

### CARE_MANAGER

A human actor with role CARE_MANAGER may resolve as an authorized override.

Care Manager override does not:

- change assignedTo
- change assignedRole
- create transfer
- take ownership

---

## 4. Denied actors

The following must be denied:

- unassigned Care Action
- non-owner Caregiver
- AI actor
- SYSTEM actor
- empty actorId
- empty actorRole
- unknown Care Action
- PENDING Care Action
- already RESOLVED Care Action

AI must never autonomously resolve a Care Action.

SYSTEM must never autonomously resolve a Care Action.

---

## 5. State transition

Authorized transition:

IN_REVIEW
->
RESOLVED

No other state transition is authorized by STEP 7J.

---

## 6. Required resolution data

Resolution requires:

- careNote
- resolutionReason
- actorId
- actorRole

careNote must describe the human care activity, observation, or outcome.

resolutionReason must state why the action is considered completed.

Both values must be non-empty human-entered content.

---

## 7. Ownership contract

Resolution must not modify:

- assignedTo
- assignedRole
- assignedAt
- priority
- dueAt

No responsibility transfer is created.

The person performing the resolution may differ from the assigned owner only when acting as SUPERVISOR or CARE_MANAGER override.

---

## 8. Audit contract

Successful resolution creates exactly one:

RESOLVED

audit event.

Expected normal audit sequence:

CREATED
->
ASSIGNED
->
REVIEW_STARTED
->
RESOLVED

The RESOLVED audit event records:

- actorId
- actorRole
- previous state
- new state
- careNote
- resolutionReason
- resolved timestamp

---

## 9. Failure contract

Business authorization rejections must return HTTP 400.

Unknown Care Action must return HTTP 404.

Internal unexpected failures remain HTTP 500.

Rejected requests must not:

- change status
- set resolved timestamp
- change ownership
- create transfer
- create RESOLVED audit event

---

## 10. Concurrency contract

If two authorized actors attempt resolution simultaneously:

- SELECT FOR UPDATE must serialize access
- exactly one request may succeed
- exactly one request returns success
- the second request must fail after observing RESOLVED state
- exactly one RESOLVED audit event exists
- ownership remains unchanged
- no transfer is created

---

## 11. AI safety boundary

AI may:

- generate warning information
- recommend review
- provide supporting analysis

AI may not:

- assign responsibility
- start review
- resolve Care Action
- write careNote as autonomous clinical action
- write resolutionReason as autonomous clinical decision
- alter ownership

Human review and human authorization remain mandatory.
