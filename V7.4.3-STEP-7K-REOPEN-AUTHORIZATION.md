# TAM AN CARE V7.4.3
# STEP 7K — CARE ACTION REOPEN AUTHORIZATION

## PURPOSE

Define the human authorization boundary for reopening a Care Action
after it has already been resolved.

This step is DESIGN ONLY.

No source code change.
No database schema change.
No runtime replacement.
No production change.

---

## TRANSITION

Allowed transition:

RESOLVED -> IN_REVIEW

A reopen operation returns the Care Action directly to IN_REVIEW under the existing compatibility state machine.

The existing assigned human owner remains unchanged. Reopen represents renewed human review of a previously resolved Care Action and does not create a new assignment.

---

## PRECONDITIONS

A Care Action may be reopened only when:

1. Care Action exists.
2. Current status is RESOLVED.
3. resolvedAt is present.
4. A human actor is explicitly identified.
5. actorRole is explicitly identified.
6. Reopen reason is explicitly provided.
7. Actor is authorized under the policy below.

---

## AUTHORIZED ACTORS

### SUPERVISOR

Allowed to reopen.

### CARE_MANAGER

Allowed to reopen.

### ORIGINAL ASSIGNED OWNER

Not authorized by default.

A previously assigned caregiver may not unilaterally reverse a
completed resolution.

This creates separation between execution responsibility and reopening
authority.

---

## DENIED ACTORS

Denied:

- ordinary Caregiver
- original assigned Caregiver acting only as owner
- AI
- SYSTEM
- anonymous actor
- empty actor ID
- empty actor role

AI must never reopen a Care Action autonomously.

SYSTEM must never reopen a Care Action autonomously.

---

## REOPEN REASON

A non-empty reopenReason is required.

Examples:

- new clinical observation requires renewed human review
- previously resolved concern recurred
- supervisor identified incomplete follow-up
- new resident condition invalidates previous closure

The reason must be stored in the audit trail.

---

## OWNERSHIP RULE

Reopen MUST NOT silently transfer ownership.

The existing assignedTo / assignedRole must remain unchanged during
the reopen operation.

No CareActionTransfer event is created by reopen.

If a later ownership change is required, it must use the explicit
transfer workflow.

---

## TARGET STATE

After successful reopen:

status = IN_REVIEW

resolvedAt = NULL

careNote = NULL or retained only according to current domain policy

resolutionReason = NULL or retained only according to current domain policy

startedAt is reset to the new human reopen/review timestamp according to the existing lifecycle implementation.

The implementation step must inspect the existing reopen() behavior
before deciding which historical fields are cleared versus preserved.

No assumption shall be made in the design step.

---

## AUDIT

Successful reopen creates exactly one:

REOPENED

audit event.

Required actor metadata:

actorId
actorRole

Required state history:

previousState
newState

Audit must show:

RESOLVED -> IN_REVIEW

---

## CONCURRENCY

Two authorized humans may attempt reopen simultaneously.

Required result:

exactly one succeeds.

The second request must fail as a business rejection.

Required database result:

one REOPENED event only.

No duplicate lifecycle transition.
No transfer.
No owner mutation.

SELECT ... FOR UPDATE must be used inside the transaction before
authorization and state mutation.

---

## HUMAN-IN-THE-LOOP BOUNDARY

AI may detect a reason to reconsider a resolved Care Action.

AI may recommend human review.

AI may not execute reopen.

A human Supervisor or Care Manager must make the reopening decision.

autonomousClinicalAction = false

---

## HTTP CONTRACT

Expected business rejections:

HTTP 400

Examples:

- action not RESOLVED
- actor unauthorized
- AI actor
- SYSTEM actor
- missing reopen reason
- duplicate reopen

Unknown Care Action:

HTTP 404

Unexpected infrastructure/internal failures:

HTTP 500
