# Tam An Care V7.5 — STEP 9F.B0
## Minimal Staff Read API Design

### 1. Architectural decision

Expose a minimal read-only HTTP surface for canonical human staff identity.

The implementation MUST reuse the existing StaffActorService.

No new staff persistence model shall be introduced.

No schema change is required.

### 2. Route namespace

Canonical namespace:

/api/operations/staff-actors

### 3. Endpoint A — Staff list

GET /api/operations/staff-actors

Optional query parameters:

- status
- role
- limit

Allowed status:

- ACTIVE
- INACTIVE
- SUSPENDED
- ARCHIVED
- ALL

Allowed role:

- CAREGIVER
- NURSE
- SUPERVISOR
- CARE_MANAGER
- ALL

Default limit:

50

Maximum limit:

100

The bounded-read policy of StaffActorService must be preserved.

### 4. Endpoint B — Staff detail

GET /api/operations/staff-actors/:actorId

Purpose:

- inspect canonical staff identity
- support staff detail UI
- support assignment workflow context

Unknown actor:

404

### 5. Authority

Both endpoints require:

- canonical actor exists
- actor status = ACTIVE
- canonical role = SUPERVISOR
- claimed role = SUPERVISOR

CAREGIVER:

DENIED

NURSE:

DENIED

CARE_MANAGER:

DENIED in V7.5 unless later explicitly expanded

AI:

DENIED

SYSTEM:

DENIED

Frontend authorization remains UX only.

Backend authorization remains authoritative.

### 6. HTTP semantics

No actor:

401

Known non-Supervisor human actor:

403

AI / SYSTEM:

403

Unknown target actor:

404

Invalid query value:

400

Success:

200

### 7. Response DTO

actorId
staffCode
displayName
primaryOperationalRole
status
employmentReference
createdAt
updatedAt

Database snake_case names must not become the required public frontend contract.

### 8. Staff list response

Recommended shape:

{
  items: StaffActorDto[],
  count: number,
  limit: number
}

No pagination expansion is required in V7.5.

### 9. Mapping

actor_id -> actorId
staff_code -> staffCode
display_name -> displayName
primary_operational_role -> primaryOperationalRole
status -> status
employment_reference -> employmentReference
created_at -> createdAt
updated_at -> updatedAt

### 10. Filtering strategy

Filtering must occur in the backend.

Frontend must not fetch an unbounded staff registry.

Any StaffActorService extension must remain:

- SELECT only
- parameterized
- bounded
- canonical

### 11. Mutation prohibition

StaffActor HTTP controller exposes GET only.

Forbidden:

- POST staff
- PUT staff
- PATCH staff
- DELETE staff
- role changes
- lifecycle changes

Staff lifecycle administration is outside current V7.5 scope.

### 12. Access administration remains separate

Existing authoritative endpoints remain:

GET /api/operations/access-assignments
GET /api/operations/residents/:residentId/access-assignments
POST /api/operations/residents/:residentId/access-assignments
POST /api/operations/access-assignments/:assignmentId/revoke

The StaffActor read API must not duplicate assignment mutation logic.

### 13. Assignment eligibility

Valid current assignment combinations:

CAREGIVER + DIRECT_CARE
NURSE + CLINICAL_CARE

SUPERVISOR and CARE_MANAGER are not current assignment target roles.

### 14. Security boundary

Frontend must not:

- query PostgreSQL directly
- fabricate staff records
- use fixture identities as operational data
- infer backend authorization from UI state

Backend remains authority source.

### 15. Expected implementation footprint

Expected backend files:

api/src/staff-actors/staff-actor.controller.ts
api/src/staff-actors/staff-actor.module.ts

Possible minimal extension:

api/src/staff-actors/staff-actor.service.ts

No schema change.

### 16. Implementation acceptance

B1 must prove:

- GET list route mapped
- GET detail route mapped
- Supervisor 200
- no actor 401
- Caregiver 403
- Nurse 403
- AI/System denial
- max limit 100
- role filter
- status filter
- unknown actor 404
- no POST/PUT/PATCH/DELETE staff routes
- SELECT-only staff read path
- Nest build pass
- isolated candidate acceptance
- zero database mutation
- schema unchanged
- production unchanged
