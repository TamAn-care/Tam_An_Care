# Tam An Care V7.4.3 — Step 8D.B

## Exact Resident Authorization Contract

### Architectural decision

CREATE_MINIMAL_CANONICAL_RESIDENT_ACCESS_MODEL

Canonical persistence target:

resident_access_assignments

Step 8D.B is design-only.
The table must not be created during this step.

### Existing assignment models

The following are domain-specific and must not become
the canonical resident-access source:

- incident_assignments
- safeguarding_assignments
- care task assigned_to
- care action assigned_to
- medication administration assigned_to
- other domain owner or reviewer fields

Domain responsibility is not the same as general resident
read authorization.

### Identity boundary

Current actor identity contract:

- x-actor-id
- x-actor-role

No canonical staff/user persistence model has been proven.

Therefore:

- do not invent a staff/user foreign key
- actor_id remains text for this model
- authentication hardening remains a separate concern
- authorization remains server-side

### Canonical logical persistence model

Table:

resident_access_assignments

Logical fields:

- resident_access_assignment_id text primary key
- resident_id text not null
- actor_id text not null
- actor_role text not null
- access_scope text not null
- status text not null
- effective_from timestamptz not null
- effective_to timestamptz null
- assigned_by text not null
- assigned_by_role text not null
- assigned_at timestamptz not null
- revoked_by text null
- revoked_by_role text null
- revoked_at timestamptz null
- revocation_reason text null
- created_at timestamptz not null
- updated_at timestamptz not null

Required foreign key:

resident_id references residents(resident_id)

No actor foreign key until canonical identity persistence exists.

### Access scopes

CAREGIVER:
DIRECT_CARE

CLINICAL_CARE

Actor role and access scope must agree.

Mismatch fails closed.

### Assignment lifecycle

Allowed states:

ACTIVE
REVOKED

Access is granted only when:

status = ACTIVE

effective_from <= current time

and:

effective_to is null
or
effective_to > current time

and actor/resident/role/scope all match.

REVOKED assignments never grant access.

Expired assignments never grant access.

### CAREGIVER policy

CAREGIVER can read only residents with a current ACTIVE
DIRECT_CARE assignment matching actor_id and resident_id.

No valid assignment:

FAIL CLOSED.

Resident endpoint behavior:

non-disclosing 404.

Dashboard:

omit all unassigned residents and all work/attention
belonging to those residents.

### NURSE policy

NURSE can read only residents with a current ACTIVE
CLINICAL_CARE assignment matching actor_id and resident_id.

No valid assignment:

FAIL CLOSED.

Resident endpoint behavior:

non-disclosing 404.

Dashboard:

omit all unassigned residents and associated operational data.

### SUPERVISOR policy

SUPERVISOR uses explicit policy:

SUPERVISORY_ALL_ACTIVE_RESIDENTS

This permits supervisory read visibility across active
residents.

It does not create mutation or clinical authority.

### Step 8B shared authorization rule

Step 8B must use the canonical resident-scope service.

Required sequence:

1. authenticate/validate actor headers
2. validate role
3. resolve canonical resident scope
4. deny unauthorized resident using non-disclosing 404
5. only then return resident operational care view

Unknown resident:

404

Unauthorized existing resident:

404

Externally indistinguishable.

### Step 8C shared authorization rule

Step 8C dashboard must use the same canonical rule.

For CAREGIVER and NURSE:

all dashboard domains must filter using the same authorized
resident set.

For SUPERVISOR:

authorized resident set is all active residents.

Forbidden:

- fetch all residents then filter only in application memory
- per-resident authorization query
- N+1 authorization
- call Step 8B once per resident
- trust arbitrary residentId from client

### Set-based authorization contract

Conceptual direct assignment predicate:

EXISTS (
  SELECT 1
  FROM resident_access_assignments raa
  WHERE raa.resident_id = r.resident_id
    AND raa.actor_id = actor_id_parameter
    AND raa.actor_role = actor_role_parameter
    AND raa.status = 'ACTIVE'
    AND raa.effective_from <= NOW()
    AND (
      raa.effective_to IS NULL
      OR raa.effective_to > NOW()
    )
)

Dashboard must use an authorized resident set conceptually
equivalent to:

authorized_residents =
active residents joined to current matching
resident_access_assignments.

Complexity target:

O(fixed source domains)

Forbidden:

O(number of residents)

revoked_at
revocation_reason

Do not delete assignment rows merely to revoke access.
