# TAM AN CARE V7.5
## STEP 9B — FRONTEND / BACKEND INTEGRATION CONTRACT

Status: LOCKED

---

# 1. Authority source

Backend is canonical authority.

Frontend role visibility is UX only.

---

# 2. Initial backend base

Development API:

http://127.0.0.1:3100

Frontend must use configurable base URL.

No production URL is locked in Step 9B.

---

# 3. Canonical actor headers

Human requests use centralized actor/session context.

Current accepted backend contract uses:

x-actor-id
x-actor-role

Components shall never manually construct these headers.

The shared API client injects them.

---

# 4. Initial endpoint families

Initial UI integration targets include:

GET /api/health

GET /api/operations/dashboard

GET /api/operations/residents/:residentId/care-view

GET /api/operations/access-assignments

GET /api/operations/residents/:residentId/access-assignments

POST /api/operations/residents/:residentId/access-assignments

POST /api/operations/access-assignments/:assignmentId/revoke

Existing resident and integration APIs shall be discovered and reused before
new backend endpoints are proposed.

---

# 5. HTTP semantics

Frontend SHALL preserve accepted backend semantics.

401:
identity/session missing.

403:
known request but authority denied.

404:
resource unavailable, including non-disclosing authorization failure.

409:
conflict such as duplicate active assignment.

Frontend must not reinterpret 404 as proof that the resident does not exist.

---

# 6. Mutation policy

Frontend mutations:

- use only explicit backend mutation routes
- never fake optimistic success for safety-critical actions
- show pending state
- prevent accidental double submit
- refresh relevant queries after success
- show backend conflict/error accurately

---

# 7. Query policy

Server-state caching must be bounded and conservative for care operations.

Critical views should support explicit refresh.

Do not keep stale resident authority indefinitely.

---

# 8. Connectivity

Global shell exposes backend connectivity.

Loss of connectivity must not silently appear as an empty dataset.

---

# 9. API type strategy

TypeScript frontend DTOs shall represent observed API contracts.

Do not invent domain fields not returned by backend.

If a UI workflow lacks required backend data, record the gap and escalate it
through the controlled roadmap before backend modification.

---

# 10. Security boundary

Frontend SHALL NOT:

- bypass 401/403/404 behavior
- infer broader resident access from dashboard output
- cache permanent authority independently
- expose AI/SYSTEM as human roles
- provide a generic database editor
- provide arbitrary PATCH/DELETE controls

---

# 11. Development-only actor bootstrap

Because full external identity provider integration is outside the current
accepted backend boundary, Step 9C may implement a controlled development
actor bootstrap mechanism.

It must be:

- clearly development-only
- centralized
- replaceable
- impossible to mistake for production authentication

A production authentication model must be separately locked before production
deployment.

---

# 12. Backend-first compatibility rule

Before requesting new backend work, frontend implementation must prove that:

1. an accepted user workflow requires missing data or behavior
2. the capability is not already available from existing APIs
3. client composition cannot solve it safely
4. the proposed backend change is minimal

This preserves the V7.4.3 backend baseline.
