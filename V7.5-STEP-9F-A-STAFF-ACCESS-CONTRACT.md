# Tam An Care V7.5 — STEP 9F.A
## Staff & Access Administration UI Contract

### 1. Purpose

Deliver a Supervisor-operated UI for staff identity visibility and resident-access administration.

The backend remains the authority source.

Frontend role logic is UX only.

---

## 2. Staff identity UI

The UI shall display canonical human actors using the existing `staff_actors` model.

Minimum visible fields:

- actorId
- staffCode
- displayName
- primaryOperationalRole
- status
- employmentReference

Human roles:

- CAREGIVER
- NURSE
- SUPERVISOR
- CARE_MANAGER

Lifecycle:

- ACTIVE
- INACTIVE
- SUSPENDED
- ARCHIVED

AI and SYSTEM are not human staff identities.

---

## 3. Staff list behavior

The first 9F implementation shall be list-first.

Required:

- staff list
- search
- role filter
- lifecycle/status filter
- clear Vietnamese labels
- responsive desktop/mobile presentation
- loading state
- empty state
- error state

No uncontrolled staff CRUD shall be added.

If the backend does not currently expose staff creation/update endpoints, the frontend shall not invent them.

---

## 4. Access administration

Supervisor-only UX.

Required administration capabilities:

- list access assignments
- list assignments by resident
- create CAREGIVER assignment
- create NURSE assignment
- revoke assignment
- display active/revoked status
- display effective period
- display server-derived audit information
- duplicate 409 feedback
- validation feedback
- read-after-write refresh
- read-after-revoke refresh

---

## 5. Authority

Only canonical ACTIVE SUPERVISOR authority may perform access administration.

CAREGIVER and NURSE shall not receive administration mutation controls.

AI and SYSTEM shall not receive human administration authority.

Frontend hiding is not security.

Backend authorization remains canonical.

---

## 6. Non-disclosure

Existing 401 / 403 / 404 semantics must be preserved.

The frontend shall not transform a backend non-disclosure response into information revealing resident or actor existence.

---

## 7. Mutation policy

9F may mutate only resident access assignments through existing backend APIs.

9F shall not:

- write directly to PostgreSQL
- create staff actors directly
- edit staff actors directly
- delete staff actors directly
- modify residents
- modify care-domain records
- modify schema.sql
- modify V7.4.3 backend

---

## 8. UX flow

Supervisor workflow:

Staff & Access
→ select/search staff
→ inspect staff identity/status
→ inspect current access
→ select resident
→ choose CAREGIVER or NURSE assignment as allowed
→ set effectiveFrom
→ submit
→ receive backend result
→ refresh assignment list
→ optionally revoke
→ refresh
→ show audit state

---

## 10. Acceptance

9F implementation must prove:

- frontend build
- supervisor positive administration
- caregiver administration denial
- nurse administration denial
- valid caregiver create
- valid nurse create
- invalid/noncanonical target denial
- duplicate 409
- read-after-write
- revoke
- read-after-revoke
- revoke idempotency
- audit display compatibility
- concurrent reads
- zero unrelated mutation
- cleanup
- final database clean
- backend/source/schema immutability
