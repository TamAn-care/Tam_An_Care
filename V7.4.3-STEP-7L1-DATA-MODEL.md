# TAM AN CARE V7.4.3
# STEP 7L.1 — CARE PLAN / CARE TASK DATA MODEL

STATUS: DESIGN ONLY
DATABASE APPLY: NO

## 1. AGGREGATE MODEL

Resident
  -> Care Plan
      -> Care Task

A Resident may have multiple Care Plans over time.

A Care Plan belongs to exactly one Resident.

A Care Task belongs to exactly one Care Plan
and exactly one Resident.

The residentId on Care Task is intentionally retained
for traceability, filtering and integrity validation.

## 3. CARE PLAN STATES

DRAFT
ACTIVE
SUSPENDED
COMPLETED
CANCELLED

## 4. CARE PLAN RULES

Every Care Plan must reference an existing Resident.

plan_code must be unique.

effective_to must not be earlier than effective_from.

ACTIVE Care Plan must eventually require approval metadata
through application policy.

Database constraints should enforce structural integrity,
while human authorization remains application-domain policy.

## 9. SCHEDULING

scheduled_at:
expected execution time.

due_at:
latest expected completion or attention time.

Rule:

due_at >= scheduled_at
when both are present.

## 10. RECURRENCE

recurrence_rule is nullable text.

It is intended to later support deterministic scheduling metadata.

Step 7L.1 does NOT define a recurrence engine.

Step 7L.1 does NOT create recurring instances.

## 11. OWNERSHIP

A task may initially be unassigned.

assigned_to
assigned_role
assigned_at

must move together under application policy.

Database alone must not decide assignment authorization.

## 12. EXECUTION TIMESTAMPS

accepted_at
started_at
completed_at
missed_at
skipped_at
cancelled_at

represent lifecycle evidence.

Only timestamps relevant to the final state
should normally be populated.

Detailed lifecycle invariant enforcement remains
primarily application logic for V7.4.3.

## 17. DELETE PRINCIPLE

No cascading delete is proposed.

Clinical/care traceability should not disappear
because a parent entity is deleted.

Future implementation should prefer controlled lifecycle state
over destructive deletion.

## 18. CONCURRENCY PRINCIPLE

Future state-changing methods should use:

SELECT ... FOR UPDATE

or equivalent transaction locking.

Single-authoritative transitions must produce:

EXACTLY ONE SUCCESS

where concurrency exists.

## 19. AI BOUNDARY

AI may propose or recommend.

AI must not directly persist:

plan activation
task assignment
task start
task completion
task skip
task cancellation

AUTONOMOUS_CLINICAL_ACTION=false
