# TAM AN CARE V7.4.3
# STEP 7L — CARE PLAN / CARE TASK DOMAIN DESIGN

STATUS: DESIGN BASELINE

## 1. PURPOSE

The Care Plan / Care Task domain converts agreed human care intentions
into structured, traceable daily care work for a Resident.

The domain MUST preserve the existing V7.4.3 principle:

AI may analyze, detect, recommend, prioritize or summarize.

AI MUST NOT autonomously:
- create executable clinical care obligations,
- accept responsibility,
- assign a human worker,
- mark a care task completed,
- skip a required care task,
- cancel a care plan,
- certify clinical completion.

Human accountability remains explicit and auditable.

## 2. DOMAIN RELATIONSHIPS

Canonical high-level relationship:

Resident
  -> Care Plan
      -> Care Task

Optional relationship:

Care Action
  -> may inform or propose change to a Care Plan

But:

Care Action != Care Plan
Care Action != Care Task

A Care Action represents a reviewed issue requiring human action.

A Care Plan represents an approved structured plan of care.

A Care Task represents an executable human care activity.

## 3. CARE PLAN IDENTITY

Every Care Plan must belong to exactly one Resident.

Proposed conceptual fields:

- carePlanId
- residentId
- planCode
- title
- description
- effectiveFrom
- effectiveTo
- status
- createdBy
- createdByRole
- approvedBy
- approvedByRole
- approvedAt
- createdAt
- updatedAt

## 4. CARE PLAN STATUS MODEL

Proposed statuses:

DRAFT
ACTIVE
SUSPENDED
COMPLETED
CANCELLED

Canonical lifecycle:

DRAFT
  -> ACTIVE

ACTIVE
  -> SUSPENDED
  -> COMPLETED
  -> CANCELLED

SUSPENDED
  -> ACTIVE
  -> CANCELLED

No autonomous AI transition is permitted.

## 5. HUMAN PLAN APPROVAL

A DRAFT Care Plan must not become ACTIVE without explicit human approval.

Initial authorization proposal:

CAREGIVER:
- may contribute information
- may view assigned/authorized plans
- may not independently activate a plan

SUPERVISOR:
- may activate according to policy
- may suspend according to policy

CARE_MANAGER:
- may activate according to policy
- may suspend according to policy
- may complete/cancel according to policy

AI:
- denied state-changing authority

SYSTEM:
- denied autonomous clinical state-changing authority

Final role matrix must be validated before implementation.

## 7. CARE TASK STATUS MODEL

Proposed statuses:

PLANNED
ASSIGNED
IN_PROGRESS
COMPLETED
MISSED
SKIPPED
CANCELLED

Canonical normal path:

PLANNED

  -> IN_PROGRESS

Exception paths:

PLANNED
  -> CANCELLED

ASSIGNED
  -> MISSED
  -> SKIPPED
  -> CANCELLED

IN_PROGRESS
  -> COMPLETED

The exact transition matrix must be frozen before coding.

## 8. ASSIGNMENT PRINCIPLE

Care Task assignment represents responsibility for a concrete care activity.

Assignment MUST be human-controlled.

AI may recommend:
- candidate caregiver
- workload balancing
- priority
- timing

AI MUST NOT independently persist assignment.

Assignment changes must be auditable.

Concurrent assignment attempts must produce one authoritative owner.

## 9. TASK EXECUTION PRINCIPLE

Only an authorized human actor may:

- accept a task
- start a task
- complete a task
- mark a task skipped
- document completion
- record exception reason

The actor identity and role must be recorded.

## 10. COMPLETION REQUIREMENTS

Task completion should require:

- task is in an executable state
- authorized human actor
- human actor identity
- completion timestamp
- completion note where policy requires it

Clinical or high-risk task categories may require stricter completion evidence.

That stricter clinical evidence model is NOT implemented in Step 7L.

## 11. MISSED TASK PRINCIPLE

A task becoming overdue does NOT mean AI has made a clinical decision.

System logic may identify:

DUE
OVERDUE
POTENTIALLY_MISSED

Human policy determines whether the task is formally recorded as MISSED,
SKIPPED, rescheduled or otherwise handled.

## 12. RECURRENCE PRINCIPLE

Recurring care work may originate from an ACTIVE Care Plan.

Examples:

- medication support reminder
- hydration support
- meal support
- mobility assistance
- personal hygiene
- observation
- social activity
- scheduled measurement

Recurrence generation must be deterministic and auditable.

Recurring task generation is administrative scheduling logic,
not autonomous clinical decision-making.

## 13. CARE ACTION -> CARE PLAN BOUNDARY

Existing Care Action flow:

Warning
-> Human Review
-> Care Action
-> Human Responsibility
-> Review
-> Resolution/Reopen

A Care Action MAY lead a human actor to:

- create a Care Plan proposal
- amend an existing Care Plan
- create a one-time Care Task proposal

But Step 7L MUST NOT automatically convert
an AI warning or Care Action into an executable Care Task.

Human approval remains required.

## 14. AUDIT REQUIREMENTS

Care Plan audit events should eventually include:

PLAN_CREATED
PLAN_ACTIVATED
PLAN_SUSPENDED
PLAN_REACTIVATED
PLAN_COMPLETED
PLAN_CANCELLED
PLAN_UPDATED

Care Task audit events should eventually include:

TASK_CREATED
TASK_ASSIGNED
TASK_REASSIGNED
TASK_STARTED
TASK_COMPLETED
TASK_MISSED
TASK_SKIPPED
TASK_CANCELLED

Every state-changing audit event should contain:

- actorId
- actorRole
- previousState
- newState
- timestamp

## 15. CONCURRENCY REQUIREMENTS

Concurrency controls will be required for at least:

- Care Plan activation
- Care Plan suspension
- task responsibility acceptance
- task assignment/reassignment
- task start
- task completion
- skip/cancel operations

Where a single-authoritative transition is required:

EXACTLY ONE SUCCESS

must be the default concurrency contract.

## 16. DATABASE SAFETY PRINCIPLE

No Care Plan / Care Task database table is created in Step 7L.

Database design must occur in a later confirmed step.

Before schema change:

1. verify current source baseline
2. verify current schema baseline
3. verify development DB identity
4. backup development schema
5. validate DDL using rollback transaction
6. apply only to isolated development DB
7. verify production schema unchanged

## 17. API SAFETY PRINCIPLE

No Care Plan / Care Task API endpoint is created in Step 7L.

Future API design should separate:

Care Plan resources

/api/care-plans

from:

Care Task resources

/api/care-tasks

Exact route design is deferred.

## 18. SECURITY / AUTHORIZATION PRINCIPLE

Authorization must be explicit.

Role text supplied by a client alone must not be considered sufficient
for a future production-grade security boundary.

Current V7.4.3 development role-policy patterns may be used for
domain behavior prototyping.

Future authentication / RBAC hardening remains a separate concern.

## 19. AI GOVERNANCE BOUNDARY

AI MAY:

- identify risk
- detect patterns
- recommend tasks
- suggest priorities
- suggest workload distribution
- suggest plan review
- summarize task history
- flag overdue tasks

AI MUST NOT:

- activate a care plan
- assign itself responsibility
- assign a human without authorization
- begin care execution
- complete a care task
- falsify completion evidence
- skip a task
- cancel a clinical task
- certify clinical outcome

autonomousClinicalAction = false

remains the governing V7.4.3 principle.

## 20. STEP 7L EXIT CRITERIA

Step 7L is complete only if:

- application source remains unchanged
- schema remains unchanged
- development database remains clean
- development runtime remains unchanged
- Production V7.4.2 remains unchanged
- design is saved
- authorization matrix is saved
- task lifecycle is saved
- AI/human boundary is saved
- design hashes are locked

No implementation is permitted during Step 7L.
