# Tam An Care V7.4.3
# STEP 8C.B
# Exact Operational Dashboard Contract

## 1. Purpose

This contract locks the exact API shape and operational semantics for
Step 8C.

Step 8C remains a computed read model above Step 8B.

No new persistence is introduced.

## 2. Endpoint

Preferred endpoint:

GET /api/operations/dashboard

The dashboard endpoint is GET-only.

No POST, PUT, PATCH or DELETE is permitted on the dashboard read surface.

## 8. Work Queue Inclusion

Include care tasks that are not terminal.

## 9. Task Operational State

Allowed computed presentation states:

MISSED
OVERDUE
DUE
SCHEDULED
ASSIGNED
IN_PROGRESS
PLANNED

Exact derivation:

MISSED:
sourceStatus == MISSED

OVERDUE:
sourceStatus is non-terminal
AND dueAt exists
AND dueAt < generatedAt
AND sourceStatus != MISSED

DUE:
sourceStatus is non-terminal
AND dueAt exists
AND dueAt >= generatedAt
AND dueAt <= generatedAt + 24 hours

IN_PROGRESS:
sourceStatus == IN_PROGRESS

ASSIGNED:
sourceStatus == ASSIGNED

SCHEDULED:
scheduledAt exists
AND no stronger state above applies

PLANNED:
fallback for PLANNED source records.

These are display classifications only.

They must not mutate care_tasks.status.

## 10. Task Ordering

Work queue sorting is deterministic.

Sort by:

1. operationalState rank
2. sourcePriority rank
3. dueAt ascending, null last
4. scheduledAt ascending, null last
5. sourceTimestamp descending
6. sourceRecordId ascending

Operational state rank:

MISSED = 1
OVERDUE = 2
DUE = 3
IN_PROGRESS = 4
ASSIGNED = 5
SCHEDULED = 6
PLANNED = 7

Source priority rank:

HIGH = 1
MODERATE = 2
LOW = 3

This ranking is presentation ordering only.

It does not change source priority.

## 12. Task Attention Mapping

Create TASK attention when:

source status == MISSED

or

non-terminal task has dueAt < generatedAt.

attentionCode:

TASK_MISSED
TASK_OVERDUE

No task status mutation is allowed.

## 13. Clinical Attention Mapping

Create CLINICAL attention only from explicit source facts.

Allowed conditions:

abnormalFlag == true

or

source status == RECORDED
and record has not yet been verified.

attentionCode:

CLINICAL_ABNORMAL_FLAG
CLINICAL_REVIEW_PENDING

The dashboard must not define new numeric clinical thresholds.

The dashboard must not diagnose.

## 14. Medication Order Attention Mapping

Create MEDICATION_ORDER attention from explicit source facts:

highRisk == true

doubleCheckRequired == true

attentionCode:

MEDICATION_HIGH_RISK
MEDICATION_DOUBLE_CHECK_REQUIRED

These are awareness flags only.

They do not authorize medication action.

## 15. Medication Administration Attention Mapping

Create MEDICATION_ADMINISTRATION attention when source status is:

MISSED
REFUSED
HELD

attentionCode:

MEDICATION_ADMIN_MISSED
MEDICATION_ADMIN_REFUSED
MEDICATION_ADMIN_HELD

The dashboard must not administer, hold, reschedule or discontinue medication.

## 16. Incident Attention Mapping

Create INCIDENT attention when incident source status is not terminal.

Terminal states:

RESOLVED
CLOSED
VOIDED

Existing currentSeverity may be surfaced if already stored.

Allowed attentionCode:

INCIDENT_OPEN
INCIDENT_HIGH
INCIDENT_CRITICAL

INCIDENT_HIGH may only be derived from currentSeverity == HIGH.

INCIDENT_CRITICAL may only be derived from currentSeverity == CRITICAL.

No severity inference is permitted.

## 17. Attention Ordering

attention[] uses deterministic ordering.

Rank categories:

1. INCIDENT_CRITICAL
2. INCIDENT_HIGH
3. MEDICATION_ADMIN_MISSED
4. TASK_MISSED
5. TASK_OVERDUE
6. CLINICAL_ABNORMAL_FLAG
7. MEDICATION_ADMIN_REFUSED
8. MEDICATION_ADMIN_HELD
9. MEDICATION_HIGH_RISK
10. MEDICATION_DOUBLE_CHECK_REQUIRED
11. CLINICAL_REVIEW_PENDING
12. INCIDENT_OPEN

Within equal rank:

sourceTimestamp ascending where operational age matters,
then residentId ascending,
then sourceRecordId ascending.

This ranking is display ordering only.

It is not a clinical severity model.

## 18. Resident Ordering

Resident navigation must be deterministic.

Initial order:

room ascending, null last
bed ascending, null last
displayName ascending
residentId ascending

No resident may be ranked clinically by the navigation list itself.

## 19. Role Visibility

### CAREGIVER

May receive:

- resident navigation permitted by current role gate
- task operational fields
- operational attention labels
- redacted clinical awareness
- redacted medication awareness
- redacted incident awareness

Must not receive fields that Step 8B redacts from CAREGIVER.

### NURSE

May receive:

- resident navigation
- care task operational information
- authorized clinical operational information
- authorized medication operational information
- incident operational information

### SUPERVISOR

May receive:

- supervisory operational dashboard
- resident navigation

- attention view
- authorized cross-domain operational detail

Role visibility must never exceed Step 8B.

## 20. Assignment Scope

Current proven enforcement:

ROLE_GATE_ONLY

Full resident assignment scope remains deferred.

Dashboard must return:

access.residentScopeEnforcement = "ROLE_GATE_ONLY"

until a separate assignment scope contract is implemented and verified.

Do not claim facility, team, shift or resident-specific enforcement yet.

## 21. Limits

Initial compact-dashboard limits are locked as:

residents: 50
workQueue: 100
attention: 100

These are maximum returned items.

Response must expose:

limits.residents
limits.workQueue
limits.attention

If more matching records exist, response must expose truncation metadata:

truncated.residents
truncated.workQueue
truncated.attention

The API must not silently truncate.

## 22. Pagination Boundary

Step 8C dashboard is a compact operational overview.

It is not a full historical browser.

Detailed pagination may be introduced later in separate endpoints.

Do not increase dashboard limits to simulate history browsing.

## 23. Summary Count Semantics

Summary counts should represent the computed candidate set before display
truncation where technically safe.

If only bounded source data is available, summary metadata must state the
scope rather than imply organization-wide completeness.

The API must not claim global counts without global data.

## 24. Availability

availability:

residents
workQueue
attention

Allowed:

AVAILABLE
EMPTY
UNAVAILABLE

AVAILABLE:
read succeeded and produced one or more relevant items.

EMPTY:
read succeeded and produced zero relevant items.

UNAVAILABLE:
source data could not be safely computed.

## 25. Partial Failure

Dashboard sections must degrade independently where safe.

A failed attention computation must not fabricate an empty attention list.

A failed section becomes UNAVAILABLE.

Errors must not silently become EMPTY.

## 26. Provenance

medication_orders

MEDICATION_ADMINISTRATION:

INCIDENT:
incidents

Dashboard-level summary/ordering metadata:

computed

## 27. Authority

authority:

readOnly: true
crossDomainMutation: false
autonomousClinicalAction: false
autonomousMedicationAction: false
autonomousIncidentAction: false
autonomousCareTaskAction: false
autonomousCarePlanAction: false

The existence of attention items does not imply action authority.

## 28. Time Contract

generatedAt is the only dashboard comparison reference time.

OVERDUE requires dueAt < generatedAt.

DUE uses a presentation horizon of 24 hours.

The 24-hour value is an operational UI horizon only.

It is not a clinical threshold.

## 29. Null Semantics

Null remains null.

Do not invent:

- due dates
- assignment
- room
- bed
- severity
- clinical measurements
- medication action status

Missing data must remain semantically absent.

## 30. Performance

The implementation must avoid:

- N+1
- one request per resident
- one request per task
- unbounded history
- audit history loading
- dashboard persistence

Preferred implementation pattern:

one bounded fixed-shape dashboard read path

or

a small fixed number of set-based queries.

Complexity must remain O(fixed source domains), not O(returned records).

## 31. Database Query Boundary

Step 8C.C0 must determine whether the safest implementation is:

A. reuse 8B service primitives without N+1

or

B. execute dedicated bounded set-based SELECT queries.

It must not choose a per-resident call to Step 8B care-view.

A loop such as:

for each resident:
  getResidentCareView(residentId)

is forbidden.
