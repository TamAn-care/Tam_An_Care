# Tam An Care V7.4.3
# STEP 8B.B — Exact DTO + Mapping + RBAC + Freshness + Performance Contract

## 1. Purpose

Step 8B.B defines the exact backend contract for the Unified Resident Care View.

It remains design-only.

No source, schema, runtime, or production mutation is permitted.

## 2. Canonical Endpoint

Preferred endpoint:

GET /api/operations/residents/:residentId/care-view

The Step 8A endpoint remains the lower-level integration source:

GET /api/integration/residents/:residentId/overview

The operational endpoint may map and summarize the Step 8A data contract but
must not introduce independent persistence.

availability:

AVAILABLE | EMPTY | UNAVAILABLE

AVAILABLE | EMPTY | UNAVAILABLE

medicationOrders:
AVAILABLE | EMPTY | UNAVAILABLE

medicationAdministrations:
AVAILABLE | EMPTY | UNAVAILABLE

incidents:
AVAILABLE | EMPTY | UNAVAILABLE

Resident remains the root existence gate.

Resident not found:
HTTP 404.

Secondary-domain failure:
HTTP 200 where safe, with the affected section marked UNAVAILABLE.

EMPTY must mean the query succeeded and returned no relevant records.

UNAVAILABLE must mean the domain could not be safely read.

## 11. Freshness DTO

freshness must not invent medical thresholds.

Recommended shape:

freshness: {
  resident: {
    sourceTimestamp: "...",
    generatedAt: "..."
  },
  carePlan: {...},
  workQueue: {...},
  clinical: {...},
  medicationOrders: {...},
  medicationAdministrations: {...},
  incidents: {...}
}

For a collection:

sourceTimestamp should be the maximum authoritative timestamp from returned
records where available.

Preferred timestamp hierarchy:

resident:
updated_at

care plan:
updated_at

care tasks:
updated_at

clinical:
measured_at first,
recorded_at second,
updated_at fallback

medication orders:
updated_at

medication administrations:
administered_at when present,
otherwise updated_at

incidents:
updated_at

Freshness is descriptive only.

Do not label data clinically stale without a separately approved policy.

## 14. RBAC Contract

Authorization is server-side.

The operational read endpoint must not weaken the existing RBAC model.

Recommended access model:

ADMIN / authorized system administrator:
may read the operational resident view according to organizational policy.

SUPERVISOR:
may read full operational care view within assigned scope.

NURSE:
may read clinically and operationally relevant sections within assigned scope.

CAREGIVER / CARE_STAFF:
may read care-task and resident-care information required for assigned work,
subject to policy.

Other roles:
deny unless explicitly authorized.

The exact role names must be mapped to existing application roles during
implementation rather than invented if the codebase uses different names.

## 15. Redaction Contract

Step 8B.C must introduce a deterministic server-side redaction layer.

Redaction may operate at:

- section level
- field level

Redaction must occur before the response leaves the server.

The client must not receive unauthorized fields and merely hide them.

Minimum rule:

No role receives broader information through the 8B view than it could
lawfully obtain from the underlying source domains.

## 16. Scope Authorization

Resident-level access must be checked where the system supports assignment,
facility, team, or organizational scope.

A valid role alone is not automatically equivalent to access to every
resident.

Step 8B implementation must preserve existing scope rules.

## 17. Mapping Rules

Source field names may be transformed from snake_case to camelCase.

Values must not be clinically reinterpreted.

Examples:

resident_id -> residentId
display_name -> displayName
care_level -> careLevel
measured_at -> measuredAt

Status strings remain source-domain values unless a separately defined
presentation category is added.

If presentation categories are added, the original source status must remain
available for provenance and auditability.

## 18. Null Handling

Null is meaningful.

Do not replace missing source values with fabricated values.

Examples:

room = null remains null
bed = null remains null
administeredAt = null remains null

UI may display a neutral placeholder.

Backend must preserve semantic absence.

## 19. Ordering Contract

Every list must have deterministic ordering.

No output may rely on physical database order.

Required tie-breakers should use stable identifiers.

## 20. Performance Contract

Initial performance contract:

- bounded domain lists
- reuse existing Step 8A per-domain limit of 20
- no N+1 queries
- parallel independent reads where safe
- no full audit-history load
- no resident-wide unbounded historical load
- no mandatory persistence cache
- no materialized operational table
- stateless request execution

Target architecture should support an operational view without requiring a
second database model.

## 21. Query Budget

The implementation should not increase query count in proportion to returned
items.

Query count should remain O(number of domains), not O(number of records).

Initial target:

resident root:
1 query

secondary Wave-1 domains:
bounded fixed set of queries

No per-task, per-medication, or per-incident follow-up query loop.

## 22. Payload Budget

No domain may return unbounded records.

Initial domain bound:
20 source records per underlying domain query.

Medication order and administration lists remain separately bounded.

Future pagination may be introduced outside the compact operational overview.

## 23. Failure Isolation

Independent secondary-domain reads should use isolated failure handling.

A failure in incidents must not automatically erase resident identity,
care-plan, task, clinical, or medication data.

Each failed domain becomes UNAVAILABLE.

Errors must not be converted silently to EMPTY.

## 24. HTTP Contract

Step 8B operational endpoint:

GET only.

No:

POST
PUT
PATCH
DELETE

for the care-view endpoint.

Mutation remains routed to authoritative source-domain workflows.

## 25. Error Contract

Resident not found:
404.

Authorization denied:
403.

Invalid request:
400 where applicable.

Secondary read failure:
prefer operational HTTP 200 with explicit UNAVAILABLE section where safe.

Unexpected server failure preventing safe root response:
5xx.

Do not expose internal SQL/database exception details to the client.

## 26. UI Boundary

Backend owns:

- authorization
- redaction
- source mapping
- availability semantics
- provenance
- freshness
- deterministic ordering
- bounded payload

UI owns:

- layout
- visual grouping
- loading states
- neutral presentation of EMPTY
- visible warning presentation of UNAVAILABLE
- navigation to authoritative workflows

UI must not reconstruct authorization rules.

## 27. Smooth Rendering Contract

Resident identity should be available as the root of the view.

Secondary sections should render independently.

One failed secondary domain should not cause the whole page to become blank.

The UI should be able to distinguish:

loading
available
empty
unavailable

without interpreting raw backend errors.

## 28. AI Boundary

AI is not required for Step 8B.

If later added, AI may:

- summarize already-authorized read data
- organize information
- highlight patterns for human review

AI may not:

- expand access permissions
- bypass redaction
- diagnose
- prescribe
- modify care plans
- complete care tasks
- administer medication
- resolve incidents
- create official records
